common-ui

Next.js · React 18/19 · 순수 HTML 에서 동일하게 쓰는 대시보드 셸 웹 컴포넌트.

설치

npm 레지스트리에 올리지 않는다. git 태그로 버전을 관리하고 소비자는 git 의존성으로 설치한다. package.json 에 한 줄을 넣는다.

태그를 반드시 지정한다. main 에는 dist/ 가 없어서 브랜치를 가리키면 설치는 되지만 import 가 실패한다. 사용할 수 있는 태그는 git tag -l 로 확인한다.

업그레이드도 이 한 줄에서 시작한다 — dashboard-common-ui.git#v0.2.5 의 태그 번호를 바꾸는 것이다. 다만 0.2.0 은 번호만 바꾸면 끝나지 않는다 — 깨지는 변경이 둘이고 코드 변경 없이 화면이 바뀌는 것이 하나다. 0.1.5 → 0.2.0 이관 을 함께 본다.

CSS 두 개를 모두 불러온다

tokens.css 는 색·치수의 단일 출처이고, controls.css 는 네이티브 요소용 .ns-* 클래스다. 컴포넌트 스타일은 토큰을 폴백 없이 참조하므로 둘 중 하나라도 빠지면 레이아웃이 무너진다.

순서는 상관없다. 토큰 이름이 전부 --ns- 접두사를 쓰므로 소비자 문서의 :root 와 겹치지 않는다. 0.1.5 까지는 접두사가 없어, 같은 이름을 다른 뜻으로 쓰던 프로젝트가 tokens.css 를 자기 CSS 뒤에 두어야만 셸 색이 살아났다.

이미 무접두사 이름(var(--space-3) 등)을 직접 참조하는 CSS 가 있는 프로젝트만 별칭 파일을 선택적으로 함께 불러온다. 새 프로젝트는 임포트하지 않는다 — 그 파일은 위의 이름 충돌을 의도적으로 재현한다.

Tailwind 를 쓰면 레이어 순서를 선언해야 한다

Tailwind v4 는 preflight 를 @layer base, 유틸을 @layer utilities 에 넣는다. controls.css 는 @layer ns-controls 로 감싸 배포되므로, 순서를 선언하지 않으면 preflight 가 이 클래스들을 지운다. 이 한 줄이 빠졌는지는 자바스크립트로 감지할 수 없다 — 유틸이 클래스를 이기는지 화면으로 확인하는 것이 유일한 수단이다.

0.2.1 → 0.2.2 이관

소비자가 할 일은 없다. 태그만 올린다. 기존 <ns-icon name="menu"></ns-icon> 은 그대로 동작한다.

ns-icon 이 기본 슬롯을 갖는다. 자식을 넣으면 그것이 그려지고 name 은 읽히지 않는다. 등록도 빌드 설정도 필요 없으므로 앱 아이콘은 대개 이쪽이 짧다. 자세한 것은 ns-icon 절의 자기 아이콘 넣기 를 본다.

손으로 HTML 을 쓸 때 <ns-icon> 안쪽에 공백을 두지 않는다. 기본 슬롯은 공백 텍스트 노드도 배정받고, 배정이 하나라도 있으면 브라우저가 폴백을 렌더하지 않는다 — 줄바꿈 하나로 아이콘이 사라진다. 콘솔 경고가 나온다. JSX 는 해당하지 않는다.

0.2.0 → 0.2.1 이관

소비자가 할 일은 없다. 태그만 올린다. 다만 사이드바 경계선을 직접 되살려 둔 CSS 가 있으면 지운다.

무엇성격해야 할 일
ns-sidebar 의 오른쪽 경계선fixns-sidebar { border-right: … } 로 되살려 둔 것이 있으면 지운다
ns-nav-group 사이 간격fix없다
registerIcons()추가없다. slot="leading" 에 <svg> 를 직접 넣던 우회를 걷어낼 수 있다
exports 의 ./package.json추가없다

경계선과 그룹 간격은 0.1.5 부터 있던 결함이고 Tailwind 를 쓰는 소비자에게만 나타났다. 둘 다 :host 에 박스 프로퍼티를 둔 것이 원인이다 — 호스트는 문서 트리에 있으므로 Tailwind preflight 의 *, ::before, ::after, ::backdrop { border: 0 solid; margin: 0; padding: 0 } 가 :host 를 이긴다. 특정도 문제가 아니라 캐스케이드 순서라 :host 쪽은 아무리 구체적이어도 진다. 0.2.1 은 두 박스를 shadow 안의 요소로 옮겼고, 문서 규칙은 거기 닿지 못한다.

그룹 간격 쪽이 보고되지 않은 이유는 증상이 조건부라서다 — 규칙이 :not(:first-child) 라 그룹이 하나뿐이면 발동하지 않는다. 두 번째 그룹을 만드는 날에 처음 나타난다.

아이콘은 ns-icon 절의 아이콘 더하기 를 본다.

0.1.5 → 0.2.0 이관

깨지는 변경이 둘, 코드 변경 없이 화면이 바뀌는 것이 하나, 새로 생긴 것이 하나다. 앞의 둘은 고치지 않으면 타입 오류나 무효한 속성으로 드러나지만, 셋째는 아무 신호 없이 모양만 달라진다.

무엇성격해야 할 일
토큰 이름에 --ns- 접두사breaking참조를 고치거나 aliases.css 를 임포트한다
React 의 NsSidebar → Sidebarbreakingimport 와 프롭 모양을 함께 바꾼다
다크모드화면이 바뀐다없다. 원하지 않으면 data-theme 으로 고정한다
ns-nav-item 의 leading slot추가없다. 원하면 배지 자리에 아이콘을 넣는다

① 토큰 이름에 --ns- 가 붙는다

공개 토큰 전부가 이름을 바꿨다 — var(--space-3) → var(--ns-space-3). 0.1.5 의 무접두사 이름을 직접 참조하는 CSS 가 있으면 그 참조는 조용히 무효가 된다. 정의되지 않은 커스텀 프로퍼티를 읽은 선언은 오류가 아니라 무효 선언이라, 콘솔에도 빌드에도 아무것도 남지 않는다. 두 길 중 하나를 고른다.

  • 참조를 고친다. 이름 앞에 --ns- 를 붙이는 기계적인 치환이다. tokens.css 의 이름 하나도 없어지지 않았으므로 대응이 1:1 이다
  • aliases.css 를 임포트한다. 옛 이름을 새 이름으로 잇는 옵트인 시트다. 한 줄로 끝나지만, 무접두사 이름을 문서 :root 에 다시 정의하므로 0.1.5 의 이름 충돌을 그대로 되살린다 — 그게 이 파일의 목적이다. 참조를 고칠 여유가 없는 기존 프로젝트만 쓴다

소비자 override 는 양쪽 모두 그대로 동작한다. :root { --ns-color-accent: … } 로 이름만 바꿔 쓰면 된다 — 문서 선언이 tokens.css 를 이기는 성질은 접두사와 무관하다.

② React 의 NsSidebar 가 Sidebar 로 바뀐다

NsSidebar 래퍼는 더 이상 export 되지 않는다. 이름만 바뀐 것이 아니라 프롭 모양도 다르다 — 핸들러에 이벤트 객체가 아니라 detail 이 그대로 들어온다. 타입 검사가 두 변경을 모두 잡으므로 조용히 넘어가지 않는다.

NsNavGroup · NsNavItem 에는 shim 이 없으므로 그쪽은 그대로 onNsNavigate={(e) => …e.detail} 다. 리스너를 사이드바로 올릴 때 모양이 한 번 바뀐다 — ns-navigate 는 composed 라 사이드바에서 한 번만 들으면 되고, 그렇게 옮기면 e.detail.href 가 d.href 가 된다.

사이드바를 감싸던 래퍼 <div> 는 더 이상 필요 없다. 0.1.x 에서 하이드레이션 너비 튐을 막으려고 안내하던 우회다. Sidebar shim 이 data-ns-open 을 서버 마크업에 실어 같은 일을 하므로, 제거해도 되고 그대로 두어도 동작한다. 제거하면 래퍼에 복제해 둔 15rem/4rem 과 트랜지션 지속시간 — 라이브러리 내부 상수를 소비자가 베껴 둔 자리 — 이 함께 없어진다. 자세한 것은 SSR 과 사이드바 너비 에 있다.

③ 다크모드가 저절로 켜진다

tokens.css 가 :root 에 color-scheme: light dark 를 선언하므로 기본값이 OS 를 따르는 것이다. 라이트 전용으로 만든 앱도 사용자의 OS 가 다크면 셸·네이티브 폼 컨트롤·스크롤바가 어두워진다 — 앱 본문만 밝은 채로 남는다. 이 릴리스에서 소비자 코드 없이 화면을 바꾸는 부분은 여기 하나다.

모양을 고정하려면 :root(<html>)에 data-theme 을 세운다. 이것이 결정적인 옵트아웃이다 — 속성 선택자라 특정도가 높아 임포트 순서와 무관하게 이긴다.

자기 CSS 에서 color-scheme 을 세우고 있다면 지우고 data-theme 으로 옮긴다. 소비자의 :root { color-scheme: … } 와 tokens.css 의 :root 는 특정도가 같아 승자를 임포트 순서가 정한다 — 토큰 이름에서 없앤 그 종속이 이 한 프로퍼티에는 남아 있다. color-scheme 은 표준 프로퍼티라 --ns- 같은 이름공간을 줄 수 없기 때문이고, 특정도를 올리는 [data-theme] 만이 그 무승부를 깬다. 자세한 것은 다크모드 절에 있다.

④ ns-nav-item 에 leading slot 이 생겼다

추가만이라 이관 작업이 없다. 행 좌측이 슬롯이 되고 badge 는 그 슬롯이 비었을 때 보이는 폴백으로 옮겨졌으므로, 기존 badge 사용은 한 글자도 고치지 않아도 그대로 동작한다. 아이콘을 넣으면 배지는 저절로 사라진다 — 분기 코드가 필요 없다.

badge 문구도 함께 바뀌었다. 0.1.5 의 설명("접힌 레일에서 보이는 배지")이 접힘 전용으로 읽혀 라벨과 같은 글자를 넣은 프로젝트가 있었다 — 배지는 접힘·펼침 양쪽에서 보인다. 슬롯 크기와 함께 ns-nav-item 절에 정리돼 있다.

환경별 연동

어느 환경이든 tokens.css 와 controls.css 를 반드시 함께 불러와야 한다. 컴포넌트 스타일은 tokens.css 가 정의하는 CSS 변수를 값 없이 참조하고, .ns-* 클래스는 controls.css 에만 있다 — 둘 중 하나라도 빠지면 레이아웃이 무너진다. tokens.css 가 빠지면 콘솔에 경고가 뜨지만, controls.css 가 빠진 것은 감지되지 않는다 — 경고는 --ns-color-line 하나만 확인한다.

Next.js (App Router)

SSR 과 사이드바 너비

@lit/react 는 엘리먼트 프로퍼티를 useLayoutEffect 안에서만 설정한다. 서버 렌더 시점에는 실행되지 않으므로 Next 가 내려주는 HTML 에는 open 속성이 없다. 그래서 <Sidebar> shim 이 data-ns-open 을 함께 내보낸다 — 반응형 프로퍼티가 아닌 이름은 createComponent 가 가로채지 않고 서버 마크업에 그대로 실린다. tokens.css 의 ns-sidebar:not(:defined) 예약이 그것을 읽으므로 하이드레이션 전후로 너비가 튀지 않는다.

소비자가 할 일은 Sidebar 를 쓰는 것뿐이다. 0.1.x 의 NsSidebar 래퍼는 더 이상 export 되지 않는다 — Sidebar 가 그 자리를 대신하고, 프롭은 onNsNavigate 대신 onNavigate(인자가 detail)다. 0.1.x 에서 안내하던 래퍼 <div> 우회는 더 이상 필요 없다 — 제거해도 되고 두어도 동작한다. (ns-header 는 예약 높이가 상태에 따라 바뀌지 않으므로 원래 영향이 없다.)

다크모드

값은 light-dark() 한 줄에 둘 다 들어 있고, 신호는 color-scheme 하나다. data-theme 이 없으면 OS 설정을 따르고, light/dark 를 세우면 그것이 이긴다. color-scheme 은 상속되므로 컴포넌트 shadow 안까지 도달하고, 네이티브 폼 컨트롤·스크롤바도 함께 뒤집힌다.

기본값이 OS 를 따르는 것이라는 점을 계약으로 읽는다. 라이브러리가 :root 에 color-scheme: light dark 를 선언하므로, 라이트 전용으로 만든 앱도 사용자의 OS 가 다크면 셸·네이티브 폼 컨트롤·스크롤바가 어두워진다 — 앱 본문만 밝은 채로 남는다. 0.2.0 에서 소비자 코드 없이 화면을 바꾸는 부분은 여기 하나다.

모양을 고정하려면 :root 에 data-theme 을 세운다. 이것이 결정적인 옵트아웃이다 — 속성 선택자라 특정도가 높아 임포트 순서와 무관하게 이긴다.

이미 자기 CSS 에서 color-scheme 을 세우고 있다면 지우고 data-theme 으로 옮긴다. 소비자의 :root { color-scheme: … } 와 이 파일의 :root 는 특정도가 같아 승자를 임포트 순서가 정한다 — 토큰 이름에서 없앤 그 종속이 이 한 프로퍼티에는 그대로 남아 있다. color-scheme 은 표준 프로퍼티라 --ns- 같은 이름공간을 줄 수 없기 때문이고, 특정도를 올리는 [data-theme] 만이 그 무승부를 깬다.

요구 브라우저: Chrome 123 · Safari 17.5 · Firefox 121 이상. light-dark() 는 Firefox 120 부터지만, controls.css 가 이미 쓰는 :has() 가 Firefox 121 이라 패키지 전체의 하한은 121 이다 — 다크모드가 하한을 올린 것이 아니다.

자기 아이콘 넣기

  

    자식을 넣으면 그것이 그려진다. 기본 슬롯의 폴백이 스프라이트라,
    자식이 있으면 name 은 읽히지 않는다. 등록도 빌드 설정도 필요 없다.
    0.2.2 부터다.
  

  
  

    크기는 ns-icon 이 정한다. 넣은 것이 자기
    width/height 를 갖고 와도 — lucide 계열은 24 를 찍는다 —
    --ns-icon-size 상자에 맞춰진다. 프레젠테이션 속성은 어떤 CSS 규칙에도
    지기 때문이다. 위 데모의 마지막 아이콘은 width="40" 을 달고 있지만
    나머지와 같은 크기로 그려진다. 굳이 다르게 하려면 그 요소에 인라인
    style 을 주면 이 규칙을 이긴다.

    shadow 의 ::slotted(*) 는 shadow root 가 생긴 뒤에만 존재하므로,

    둔다. 한 벌만 있으면 자식이 자기 크기(24)로 그려지다가 하이드레이션 직후 20 으로
    줄어드는 튐이 남는다 — ns-sidebar 너비에서 없앤 것과
    같은 종류다. 둘 다 필요한 이유는 대상이 다르기 때문이다: 문서 선택자는 다른
    컴포넌트 shadow 안의 ns-icon 에 닿지 못하고, ::slotted 는
    upgrade 전에 존재하지 않는다.
  

  

    접근성은 넣는 쪽 책임이다. 스프라이트로 그릴 때 붙는
    aria-hidden 은 우리 shadow 안의 svg 에 있는 것이라 슬롯으로
    들어온 것에는 없다. lucide-react 는 스스로 붙인다.

    콘솔에 경고를 낸다. JSX 는 안전하다 — 공백만 있는 줄을 컴파일 시점에

    open 프로퍼티를 설정하면 제어 모드다. 컴포넌트는
    그 값을 바꾸지 않고 ns-dialog-close 만 올린다. 소비자가

    <ns-dialog open> 이 제어 모드로 들어가 스스로 닫지 못하게 되므로,
    그것을 피하려고 이름을 갈랐다.

    무시된다. 속성이 관찰되지 않으므로 열리지도 않고 open 프로퍼티는
    undefined 로 남아 비제어다. 이 구분이 중요한 이유는 증상이 다르기
    때문이다 — 제어 모드로 들어갔다면 "열린 채 안 닫히는" 것이고, 실제로는 "아무 일도

    경고한다. 라이브러리는 호스트에 속성을 쓰지 않으므로 이 이름의 속성이
    발견되면 언제나 소비자가 쓴 것이고, 언제나 실수다.
  

  

    같은 규칙이 ns-pagination 의 page,
    ns-table 의 sortKey·sortDirection·selected
    에도 적용된다. 전부 프로퍼티 전용이고, 속성으로 쓰면 무시되며, 이제 경고한다.
  

  

    제어에서 비제어로 되돌릴 수도 있다 — open 을 다시 undefined
    로 설정하면 비제어로 전환되고, 그 시점의 내부 상태(보통 닫힘)가 화면에 반영된다.

ns-table

  

    소비자가 쓴 table 을 감싸는 Light DOM 컴포넌트.
    셀을 렌더하지 않고 데이터를 모른다. 정렬 상태와 그 시각 표시만 갖고,
    데이터를 다시 정렬하는 것은 소비자다.
  

  

    그렇게 나눈 이유는 실사용 셀이 데이터 주입형 API 로 표현되지 않기 때문이다 —
    조건부 버튼 여섯, 참조 조회로 만든 이름, 조건부 칼럼이 들어 있다.
    Lit 엘리먼트는 소비자의 React 렌더 함수를 호출해 자기 안에 React 요소를
    만들 수 없다.
  


  
정렬 헤더는 button 을 품는다

  

    th 자체를 클릭 가능하게만 만들면 키보드로 도달할 수 없고
    화면낭독기가 상호작용 요소로 안내하지 않는다. tabindex/role="button" 을
    th 에 얹는 것은 표 의미를 깨뜨린다. 컴포넌트가 렌더를 하지 않으므로
    이것을 대신 만들어 줄 수 없다 — 셀을 소비자에게 남긴 대가다.
  

  

    data-ns-sort-key 가 없는 th 는 정렬되지 않는다. 칼럼별 스위치가 그것뿐이다.
  

  

    클릭 영역이 th 전체라는 것에는 따르는 결과가 있다 —
    정렬 헤더 안에 놓인 다른 상호작용 요소(링크·정보 아이콘·두 번째 버튼)를
    눌러도 정렬이 일어난다. 의도된 동작이지만, 그런 요소를 헤더에 넣을
    계획이라면 그 칼럼에는 data-ns-sort-key 를 붙이지 않는 편이 낫다.

    data-ns-sort-key 가 없다. 실제 목록 화면은 둘을 함께 쓰고,
    둘이 만나는 자리에서만 드러나는 동작이 있어서 이 데모를 따로 둔다.

체크하면 여기에 ns-select-change 가 찍힌다.

  

    비제어 초기값 셋이 여기 다 있다.
    default-sort-key="name" · default-sort-direction="ascending" 라
    로드 직후 "이름" 헤더에 삼각형이 올라와 있고, 마크업의 checked 하나 때문에
    전체 선택이 로드 직후부터 가로줄이다. 마크업의 행 순서도 이름 오름차순으로
    맞춰 두었다 — 데이터를 실제로 정렬하는 것은 소비자이고 컴포넌트는 초기값에
    맞춰 행을 옮겨주지 않는다.
  

  

    이 초기 선택으로는 ns-select-change 가 나가지 않는다.
    소비자가 자기 마크업에 쓴 값은 변경이 아니라 시작점이다.
  

  

    "이름" 을 누르면 ascending 다음인 descending 부터 이어진다.
    다른 칼럼("가입일")을 누르면 ascending 으로 시작한다.
  

  

    이 데모는 행을 다시 그릴 때 체크 상태를 일부러 옮기지 않는다.
    체크된 행이 있는 상태에서 정렬 헤더를 누르면 새 tbody 의 체크박스는 전부 꺼져 있고,
    컴포넌트가 그 축소를 감지해 ns-select-change  ids=[] 를 낸다 —
    두 번째 로그가 그 자리에서 바뀐다. 이 이벤트가 없으면 소비자는 화면에 없는 행을 선택된 것으로
    알고 "삭제(1건)" 을 켜 둔 채로 남는다. 실제 앱에서는 선택 집합을 소비자가 들고 있다가 다시 그릴 때
    checked 를 복원하는 편이 낫다 — 그러면 집합이 그대로라 이벤트도 나가지 않는다.
    같은 헤더를 여러 번 눌러도 집합이 이미 비어 있으면 조용하다.

방향은 3-상태다

  

    none → ascending → descending → none.
    2-상태로 하면 서버의 기본 정렬로 돌아갈 방법이 없다. 그 기본 순서가
    의도를 담는 경우가 있다 — "오래된 신청이 위" 같은 것이다.
  


  
전체 선택의 범위는 현재 페이지다

  

    DOM 에 있는 행만 대상이다. 서버 페이징에서 "전체 선택" 은 보이는 20개를
    뜻한다. "240개 전부 선택" 은 별개 기능으로 제공하지 않는다.
  

  

    제어 모드(selected 를 설정한 상태)에서는 행 체크박스의
    checked 를 컴포넌트가 건드리지 않는다. 요청되는 다음 집합만
    이벤트로 올리고, 적용은 소비자가 한다 — 컴포넌트가 쓰면 소비자의 다음
    렌더에 덮어써져 두 진실이 싸운다. 전체 선택 3-상태만은 selected 를 기준으로
    컴포넌트가 계속 쓴다.
  

  

    그래서 제어 모드는 "소비자가 ns-select-change 를 받아 각 행의
    checked 를 다시 그린다" 를 전제한다. React 에서는 그것이
    제어 입력 그대로다 — checked={selected.includes(id)} 에
    no-op onChange 를 붙이는 보통의 모양이 맞는 사용법이고, 상태를 갱신하는 것은
    onNsSelectChange 다. 순수 HTML 에서 el.selected = [...] 로만
    제어하고 되돌려 그리는 코드를 두지 않으면 사용자가 누른 박스가
    selected 와 어긋난 채로 남는다 — 컴포넌트는 그 박스를 되돌리지
    않는다. 되돌려 그릴 생각이 없다면 selected 를 설정하지 말고 비제어로 두고
    이벤트만 듣는 편이 맞다.
  

  

    0.2.5 에서는 바로 그 React 제어 체크박스가 동작하지 않았다.
    행을 눌러도 체크되지 않고 ns-select-change 의 ids 가 언제나
    그대로였다 — 콘솔도 타입 검사도 조용했다. 체크박스의 활성화는 순서가 정해져 있어서
    checked 를 뒤집고 → click 을 디스패치하고 → 그 다음
    input·change 를 디스패치하는데, React 의 제어 입력 구현은
    루트 컨테이너에서 click 을 처리하고 그 처리가 끝나는 시점에 DOM 을 프롭
    값으로 되돌린다. 0.2.5 의 ns-table 은 change 에서
    checked 를 읽었으므로 언제나 되돌려진 값을 봤다.
    지금은 click 에서 읽는다. 그 리스너는 ns-table 호스트에 붙어
    있어 버블 경로에서 React 의 루트보다 먼저 지나가므로 되돌리기 전의 값을 읽는다.
  

  

    0.2.5 에서 defaultChecked 와 ref 로 DOM 에 직접
    checked 를 쓰는 우회를 했다면 되돌려도 된다. 이제
    checked 프롭이 정상 경로다.
  

  

    프로그램으로 input.checked 를 바꾼 뒤 change 를 직접
    디스패치하는 방식은 지원하지 않는다. 이 컴포넌트는 click 만 듣는다.
    길은 둘이다. 비제어로 두고 있었다면 box.click() 이 그대로 동작한다 —
    브라우저가 checked 를 뒤집고 click 을 디스패치하므로 사용자가 누른
    것과 같은 경로이고, 0.2.5 에서도 지금도 같다. 이관이 한 줄로 끝난다.
    selected 프로퍼티를 쓰는 것도 물론 되지만, 그것은
    비제어였던 표를 제어 모드로 옮기는 것이라 계약이 달라진다 — 그 순간부터
    컴포넌트는 행 checked 를 쓰지 않고 소비자가 매번 되돌려 그려야 한다.
  


  
접근성

  

    aria-sort 의 유일한 작성자가 컴포넌트다. 소비자는 쓰지 않는다.
    삼각형은 content 문자가 아니라 border 로 그린다 — 생성된 텍스트는
    일부 브라우저에서 화면낭독기에 읽혀 aria-sort 와 중복 안내가 된다.
  

  

    정렬되지 않은 칼럼에는 aria-sort 가 붙지 않는다.
    none 은 ARIA 의 기본값이라 속성이 없는 것과 의미가 같고, 굳이 붙이면
    SSR 마크업에 없던 속성이 upgrade 때 생겨 React 가 하이드레이션 불일치를 보고한다 —
    customElements.define 은 모듈 평가 시점에 실행되므로
    hydrateRoot 보다 먼저다. 0.2.5 는 "none" 을 썼고, 정렬 헤더가
    있는 Next.js 페이지 전부에서 그 경고가 떴다.
    suppressHydrationWarning 으로는 막을 수 없다 — 그 프롭은 한 단계 아래로
    내려가지 않고 속성의 주인은 <th> 다.
  

  

    그 불일치가 남는 경우는 하나다 — default-sort-key 로 처음부터
    정렬된 표. 그때 생기는 aria-sort="ascending" 은 진짜 상태라 지울 수
    없다. 서버 마크업의 해당 <th> 에 같은 값을 직접 렌더하면 맞는다.
  

  

    소비자가 aria-sort="none" 을 직접 쓰지 않는다.
    컴포넌트가 그것을 지우므로 손으로 쓴 값 자체가 불일치가 된다.

ns-pagination

  

    목록 페이지 이동 컨트롤. 표를 모르고 데이터를 모른다 — 어떤 목록에도 붙는다.
    페이지를 실제로 바꾸는 것은 소비자다.
  

  

    Light DOM 이라 .ns-button 을 그대로 쓴다. shadow 였다면
    버튼 스타일 전부를 다시 적어야 했다 — ns-dialog 닫기 버튼에서 수용한
    열 줄짜리 중복이 여기서는 훨씬 커진다.
  

  

    자식을 받지 않는다. Lit 이 이 요소의 내용을 통째로 소유하고 렌더마다
    갈아 끼우므로 <ns-pagination>…</ns-pagination> 사이에 쓴 것은
    첫 렌더에서 사라진다. slot 이 없다. React 에서는 조용히 사라지는 것으로 끝나지
    않는다 — <NsPagination>{x}</NsPagination> 처럼 자식을 주면
    React 와 Lit 이 같은 자식을 두고 다투다 removeChild 계열 런타임 에러가 날 수
    있다. 래퍼의 프롭 타입은 children 을 막지 않으므로 타입 검사로도 걸리지 않는다.
    항상 자기 닫는 태그로 쓴다.

    탭 줄. 탭 버튼을 렌더하지 않는다 — 소비자가 쓴
    <button> 에 role·aria-selected·
    aria-controls·roving tabindex 를 채우고 화살표 키를 단다.
    ns-table 이 셀을 렌더하지 않는 것과 같은 자리다.
  

  

    shadow root 를 두지 않는다. 이 컴포넌트는 자기 마크업을 하나도
    렌더하지 않으므로 캡슐화할 것이 없고, shadow 를 두면 얻는 것 없이 실패 경로만
    생긴다 — LitElement 처럼 템플릿을 렌더하면 소비자가 쓴 버튼이 덮이고,
    <slot> 없는 shadow root 는 그 버튼을 가린다. 둘 다 에러 없이
    빈 탭 줄이 된다. 곁들여, 전역 스타일시트인 controls.css 는 shadow
    안에 닿지 않는다. aria-controls 는 이 결정의 근거가 아니다 — 슬롯을
    쓰면 탭 버튼은 문서 트리에 그대로 남으므로 IDREF 도 계속 해석된다.
  

  

    호스트에 role="tablist" 를 쓴다. ARIA 의 tablist↔tab
    소유 관계는 DOM 부모여야 해서 둘 곳이 호스트밖에 없다. 이미 role 이
    있으면 건드리지 않는다. aria-label 은 직접 쓴다.

이름위치용도

    
leading행의 좌측 끝아이콘 등. 비우면 badge 가 대신 보인다 — 슬롯 폴백이라 분기 코드가 필요 없다. 접혀도 계속 보인다. 접근성은 넣는 쪽 책임이다 — ns-icon 이 aria-hidden 을 붙이는 것은 name 으로 그린 자기 svg 뿐이다. 슬롯으로 들어온 것은 소비자 소유이므로 소비자가 붙인다 (lucide-react 는 스스로 붙인다)

    
trailing행의 우측 끝카운트 배지 등 소비자가 원하는 것. 접히면 함께 숨는다

  

  

    leading 에 넣은 것의 크기는 컴포넌트가 정하지 않는다.
    슬롯 자리는 1.75rem(--ns-control-height-sm) 정사각형이고,
    컴포넌트가 하는 일은 들어온 것이 그 상자를 넘지 못하게 상한을 씌우는 것뿐이다.
    크기는 넣은 요소가 스스로 갖는다 — <ns-icon> 은
    자기 --ns-icon-size(1.25rem = 20px)로 그려지므로 상한이
    발동하지 않는다. 크기가 없는 요소(빈 span 등)를 넣으면 이 규칙은 그것을
    키워 주지 않는다.
  

  

    0.1.x 에서 24px 아이콘을 쓰던 프로젝트는 그 항목에서 되돌린다.
    --ns-icon-size 는 상속되는 커스텀 프로퍼티이므로 아이콘 하나에만 걸면 된다.
    상자가 1.75rem(28px)이라 24px 은 상한에 닿지 않는다.
  

  
  

    :root 에서 --ns-icon-size 를 재정의하는 것은 다른 이야기다 —
    셸 전체의 아이콘(헤더 토글, 대화상자 닫기 버튼)까지 함께 커진다. 네비게이션 아이콘만
    키우려면 위처럼 그 요소에 건다.
