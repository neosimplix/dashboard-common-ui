common-ui

Next.js · React 18/19 · 순수 HTML 에서 동일하게 쓰는 대시보드 셸 웹 컴포넌트.

설치

npm 레지스트리에 올리지 않는다. git 태그로 버전을 관리하고 소비자는 git 의존성으로 설치한다. package.json 에 한 줄을 넣는다.

태그를 반드시 지정한다. main 에는 dist/ 가 없어서 브랜치를 가리키면 설치는 되지만 import 가 실패한다. 사용할 수 있는 태그는 git tag -l 로 확인한다.

업그레이드는 태그 번호만 바꾸면 된다. #v0.1.0 → #v0.2.0.

CSS 두 개를 모두 불러온다

tokens.css 는 색·치수의 단일 출처이고, controls.css 는 네이티브 요소용 .ns-* 클래스다. 컴포넌트 스타일은 토큰을 폴백 없이 참조하므로 둘 중 하나라도 빠지면 레이아웃이 무너진다.

Tailwind 를 쓰면 레이어 순서를 선언해야 한다

Tailwind v4 는 preflight 를 @layer base, 유틸을 @layer utilities 에 넣는다. controls.css 는 @layer ns-controls 로 감싸 배포되므로, 순서를 선언하지 않으면 preflight 가 이 클래스들을 지운다. 이 한 줄이 빠졌는지는 자바스크립트로 감지할 수 없다 — 유틸이 클래스를 이기는지 화면으로 확인하는 것이 유일한 수단이다.

환경별 연동

어느 환경이든 tokens.css 와 controls.css 를 반드시 함께 불러와야 한다. 컴포넌트 스타일은 tokens.css 가 정의하는 CSS 변수를 값 없이 참조하고, .ns-* 클래스는 controls.css 에만 있다 — 둘 중 하나라도 빠지면 레이아웃이 무너진다. tokens.css 가 빠지면 콘솔에 경고가 뜨지만, controls.css 가 빠진 것은 감지되지 않는다 — 경고는 --color-line 하나만 확인한다.

Next.js (App Router)

SSR 과 사이드바 너비

@lit/react 는 엘리먼트 프로퍼티를 useLayoutEffect 안에서만 설정한다. 서버 렌더 시점에는 절대 실행되지 않으므로, Next 가 내려주는 HTML 에는 <ns-sidebar></ns-sidebar> 처럼 open 속성이 아예 없다. 이 순간 tokens.css 의 ns-sidebar:not([open]) 규칙이 적용되어 4rem 레일로 그려지고, 하이드레이션 직후 open 이 참인 페이지라면 15rem 으로 벌어진다 — 기본값이 펼침인 사이드바는 매 페이지 로드마다 이 튐을 겪는다. (ns-header 는 예약 높이가 상태에 따라 바뀌지 않으므로 영향이 없다.)

우회하려면 <NsSidebar> 를 같은 상태로 너비를 지정한 <div> 로 감싸고, 사이드바 자신은 그 안을 채우게 한다.

React 18 (Vite 등)

코드가 Next 와 완전히 동일하다. 래퍼가 React 18 과 19 의 차이를 흡수한다.

순수 HTML

빌드 도구가 필요 없다. UMD 번들은 type 없는 클래식 script 로 불러야 한다 — file:// 에서 type="module" 은 CORS 로 막힌다.

  • dist/tokens.css 를 <link rel="stylesheet"> 로
  • dist/controls.css 를 <link rel="stylesheet"> 로
  • dist/bundle.umd.js 를 <script src> 로 (type 없이)

.ns-button

button 과 a 에 똑같이 붙는다. 클릭 결과가 페이지 이동이면 a, 그 자리에서 무언가 하면 button 이다.

웹 컴포넌트로 만들지 않은 이유가 여기서 가장 뚜렷하다. shadow DOM 안의 button type="submit" 은 바깥 폼을 제출하지 못하고, 텍스트 필드에서 Enter 로 제출되는 동작도 보장되지 않는다.

ns-dialog

  

    네이티브 dialog 를 showModal() 로 연다. 포커스 트랩 ·
    Esc 닫기 · 배경 inert · top layer · ::backdrop 을
    브라우저가 처리한다. 직접 구현하면 접근성을 처음부터 다시 만들어야 한다.
  

  

    slot 된 form 은 안전하다. 폼과 그 안의 입력칸은 전부
    light DOM 에 있어 제출 · 검증 · 자동완성이 정상 동작하고, 모달의 포커스 트랩은
    flat tree 를 따라가므로 slot 된 내용도 포함한다.
  


  
제어와 비제어

  

    open 프로퍼티를 설정하면 제어 모드다. 컴포넌트는
    그 값을 바꾸지 않고 ns-dialog-close 만 올린다. 소비자가
    open 을 true 로 두면 Esc 로 닫혔던 대화상자가
    다시 열린다 — 그게 제어의 정의다.
  

  

    open 을 한 번도 설정하지 않으면 비제어 모드다.
    컴포넌트가 스스로 닫고, show() / close() 로 여닫는다.
    초기값은 default-open 속성이다.
  

  

    open 은 속성이 아니라 프로퍼티다.
    <ns-dialog open> 이라고 쓰면 제어 모드로 들어가 스스로 닫지
    못하게 된다. 순수 HTML 에서는 default-open 을 쓴다.
  

  

    제어에서 비제어로 되돌릴 수도 있다 — open 을 다시 undefined
    로 설정하면 비제어로 전환되고, 그 시점의 내부 상태(보통 닫힘)가 화면에 반영된다.
    열려 있던 대화상자가 그 순간 닫힌다.

ns-table

  

    소비자가 쓴 table 을 감싸는 Light DOM 컴포넌트.
    셀을 렌더하지 않고 데이터를 모른다. 정렬 상태와 그 시각 표시만 갖고,
    데이터를 다시 정렬하는 것은 소비자다.
  

  

    그렇게 나눈 이유는 실사용 셀이 데이터 주입형 API 로 표현되지 않기 때문이다 —
    조건부 버튼 여섯, 참조 조회로 만든 이름, 조건부 칼럼이 들어 있다.
    Lit 엘리먼트는 소비자의 React 렌더 함수를 호출해 자기 안에 React 요소를
    만들 수 없다.
  


  
정렬 헤더는 button 을 품는다

  

    th 자체를 클릭 가능하게만 만들면 키보드로 도달할 수 없고
    화면낭독기가 상호작용 요소로 안내하지 않는다. tabindex/role="button" 을
    th 에 얹는 것은 표 의미를 깨뜨린다. 컴포넌트가 렌더를 하지 않으므로
    이것을 대신 만들어 줄 수 없다 — 셀을 소비자에게 남긴 대가다.
  

  

    data-ns-sort-key 가 없는 th 는 정렬되지 않는다. 칼럼별 스위치가 그것뿐이다.
  

  

    클릭 영역이 th 전체라는 것에는 따르는 결과가 있다 —
    정렬 헤더 안에 놓인 다른 상호작용 요소(링크·정보 아이콘·두 번째 버튼)를
    눌러도 정렬이 일어난다. 의도된 동작이지만, 그런 요소를 헤더에 넣을
    계획이라면 그 칼럼에는 data-ns-sort-key 를 붙이지 않는 편이 낫다.

이름detail발생 시점

방향은 3-상태다

  

    none → ascending → descending → none.
    2-상태로 하면 서버의 기본 정렬로 돌아갈 방법이 없다. 그 기본 순서가
    의도를 담는 경우가 있다 — "오래된 신청이 위" 같은 것이다.
  


  
전체 선택의 범위는 현재 페이지다

  

    DOM 에 있는 행만 대상이다. 서버 페이징에서 "전체 선택" 은 보이는 20개를
    뜻한다. "240개 전부 선택" 은 별개 기능으로 제공하지 않는다.
  

  

    제어 모드에서는 행 체크박스의 checked 를 컴포넌트가 건드리지
    않는다. React 가 그 값을 소유하므로 쓰면 다음 렌더에 덮어써진다. 요청되는
    다음 집합만 이벤트로 올리고, 적용은 소비자가 한다.
  


  
접근성

  

    aria-sort 의 유일한 작성자가 컴포넌트다. 소비자는 쓰지 않는다.
    삼각형은 content 문자가 아니라 border 로 그린다 — 생성된 텍스트는
    일부 브라우저에서 화면낭독기에 읽혀 aria-sort 와 중복 안내가 된다.
