# 커밋 메시지 규칙

이 저장소의 모든 커밋은 아래 규칙을 **반드시** 따른다. AI가 커밋 메시지를 생성하거나 제안할 때 상시 참조한다.

## 형식

```
<type>(<scope>): <subject>
```

- 한 줄 요약(제목)만으로 충분한 경우 본문은 생략한다.
- 본문이 필요하면 제목 다음에 빈 줄 하나를 두고 작성한다.

## Type

| type | 설명 |
| --- | --- |
| `feat` | 새로운 기능 추가 |
| `fix` | 버그 수정 |
| `refactor` | 버그 수정이나 기능 추가가 없는 코드 구조 개선 |
| `style` | 코드 의미 변화가 없는 포맷팅, 세미콜론 누락 등 수정 |
| `docs` | 문서 수정 (README, 주석 등) |
| `test` | 테스트 코드 추가 또는 리팩토링 |
| `chore` | 빌드 업무, 패키지 매니저 설정, 보일러플레이트 변경 등 기타 작업 |

목록에 없는 type은 쓰지 않는다.

## Scope

- 작업 영역이나 도메인을 **영어 소문자**로 명확히 명시한다. (예: `auth`, `payment`, `ui`, `shell`, `harness`, `deps`)
- 괄호 안은 리터럴 단어가 아니라 **실제 기능 식별자** 자리다. `feat(기능):` 처럼 쓰지 않는다.
- 커밋 전에 이 변경이 어떤 기능 영역인지 영어 한 단어로 정한 뒤 넣는다.
- 여러 영역에 걸친 변경은 커밋을 분리하는 것을 우선 고려하고, 불가피할 때만 대표 영역 하나를 고른다.

## Subject

- **한국어**로 작성한다.
- 명령조 / 현재 시제로 쓴다. (`추가`, `수정`, `분리` — `추가했음`, `추가할 예정` 아님)
- 첫 글자는 소문자로 시작한다. 한국어 제목에서는 영문 단어가 앞에 올 때만 해당하며, 고유명사(`ESLint`, `Next.js` 등)는 원래 표기를 유지한다.
- 끝에 마침표(`.`)를 찍지 않는다.
- 무엇을, 왜 변경했는지 드러나게 쓴다. `버그 수정`, `코드 정리` 같은 모호한 표현은 피한다.

## 예시

```
feat(auth): sso 로그인 기능 연동
fix(payment): 결제 실패 시 타임아웃 예외 처리
refactor(user): 마이페이지 프로필 조회 로직 분리
style(common): ESLint 규칙 적용에 따른 코드 포맷팅
chore(deps): axios 라이브러리 버전 업그레이드
docs(readme): 로컬 개발 환경 실행 절차 보완
test(shell): 승인 플로우 렌더링 테스트 추가
```

## 커밋 / 푸시 정책

- 작업 완료 시 **로컬 커밋까지만** 수행한다.
- `git push`는 사용자가 명시적으로 요청할 때만 실행한다.
