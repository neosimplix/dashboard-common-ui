# 릴리스 전에 사람이 봐야 하는 것

`.claude/rules/verification.md` 가 이 저장소의 회귀 확인 수단을 둘로 못박는다 — `npm run check` 와 `index.html` 육안 확인. 이 파일이 담는 것은 **두 범주**다.

- **A — `index.html` 육안 확인이 볼 목록.** 두 번째 수단은 볼 것의 목록이 있어야 작동한다.
- **B — 두 수단 **어느 쪽도** 닿지 않는 것.** `index.html` 에는 React 도 Tailwind 도 번들러도 없어서, 여기서는 재현 자체가 불가능하고 소비자 프로젝트가 있어야 확인된다. **B 는 `index.html` 확인의 일부가 아니라 세 번째 범주다.**

## 이 파일을 다루는 법

- **살아 있는 목록이다. 릴리스가 나가면 비운다.** 항목의 가치는 "바뀌었는데 아직 아무도 눈으로 안 봤다" 하나뿐이라, 확인이 끝난 항목은 소음이다. 낡은 항목이 쌓인 목록은 없는 것보다 나쁘다 — 훑고 넘기는 습관을 만들고, 그 습관은 다음 사이클의 진짜 새 항목까지 함께 넘긴다.
- **누적 로그로 만들지 않는다. 그 일은 git 이 이미 한다.** `git log -p docs/pending-human-checks.md` 가 사이클마다 무엇을 봐야 했는지를 그대로 준다. 파일 안에 이력을 또 쌓으면 중복이고, 둘이 어긋날 때 낡는 쪽은 언제나 파일 안이다.
- **비우는 법: 아래 `## 범위` · `## B` · `## A` 세 절을 통째로 지우고 `## 대기 없음` 한 줄을 남긴다.** `## 범위` 를 함께 지우는 것이 중요하다 — 그 절은 아래 목록이 무엇을 덮는지 설명하는 것이라, 목록 없이 남으면 없는 내용을 주장하는 문장이 된다. 파일 자체를 지우거나 완전히 비우지도 않는다. 그러면 "지금 정말 대기가 없다" 와 "아무도 안 채웠다" 가 구분되지 않는다.
- **비우는 시점은 태그를 자르기 전이다.** `.claude/skills/releasing/SKILL.md` 가 `## 실행` 앞에서 이 파일을 가리킨다. 남아 있는 항목은 확인되지 않은 항목이고, 태그는 되돌릴 수 없다.
- 항목을 더할 때는 **무엇을 보나** 와 **무엇이 잘못된 것인가** 를 함께 적는다. 하나만 있으면 보는 사람이 판정할 수 없고, 판정할 수 없으면 정상인 변화를 결함으로 신고하는 쪽으로 기운다. 아래 A 항목의 상당수는 그 오인을 미리 막으려고 있다.
- **B 를 A 보다 앞에 둔다.** A 는 `index.html` 을 열면 어차피 눈에 걸리지만, B 는 여기 적혀 있지 않으면 존재조차 알 수 없다.

## B. 이 저장소에서는 재현할 수 없다 — 소비자 프로젝트가 필요하다

> **`npm run check` 가 초록인 것은 아래 다섯에 대해 아무 증거도 아니다.**

`index.html` 에는 **React 가 없고, Tailwind 가 없고, 번들러가 없고, `hydrateRoot` 가 없다.** 아래 다섯은 그중 하나 이상을 필요로 한다. 소비자 프로젝트(`project01-test` — Next.js 16 · React 19 · Tailwind v4 대시보드)에서 본다.

0.2.5 사이클이 고친 넷 각각에 소비자 환경에서만 드러나는 몫이 하나씩 있다 — 설계 **§1 → B-1, §2 → B-2, §3 → B-3, §5 → B-4**. (**§4 는 항목이 없다.** `README.md` 에 `"use client"` 절을 더한 문서 전용 변경이라 볼 화면이 없다. 빠뜨린 것이 아니다.) **B-5 는 갤러리 이관 사이클 몫**이고 역시 SSR 이 있어야 관찰된다.

### B-1. React 제어 체크박스와의 조합 (0.2.5 설계 §1)

0.2.5 사이클이 고친 진짜 버그이고, **이 저장소에는 확인할 방법이 아예 없다.** `index.html` 의 체크박스는 소비자가 상태를 되돌리지 않는 순수 DOM 체크박스라, `change` → `click` 이동으로 고친 그 경합이 애초에 일어나지 않는다. **A-1 이 초록인 것은 "회귀가 없다" 는 뜻이지 "버그가 고쳐졌다" 는 뜻이 아니다.**

- `checked={selected.includes(id)}` + no-op `onChange={() => {}}` 로 쓴 표에서 행 선택이 실제로 되는지
- 0.2.5 에서 쓰던 `defaultChecked` + `ref` 우회를 **지워도** 되는지
- 전체 선택 3-상태가 React 쪽 상태와 어긋나지 않는지

**잘못된 것:** 클릭한 체크가 즉시 되돌아간다. 그것이 0.2.5 의 증상 그대로다. 메커니즘은 `src/components/table/ns-table.ts` 의 `#onClick` 주석에 있다.

### B-2. 하이드레이션 경고 소멸 — `aria-sort` (0.2.5 설계 §2)

`hydrateRoot` 가 있어야 관찰되는 현상이다. 정렬 헤더가 있는 Next.js 페이지를 열어 **콘솔이 깨끗한지** 본다. `A tree hydrated but some attributes … aria-sort="none"` 이 더는 나오지 않아야 한다.

**`default-sort-key` 로 처음부터 정렬된 표는 여전히 경고가 난다.** 그것은 진짜 상태 변화라 지울 수 없고, 그 소비자는 서버 마크업에 같은 `aria-sort` 를 직접 렌더해야 한다(`index.html` 의 SSR 안내). **그 경우까지 조용해지길 기대하지 않는다** — 기대하면 정상을 결함으로 신고하게 된다.

### B-3. CSS 임포트 자리 (0.2.5 설계 §3) — 가장 위험한 항목

레이어 순서 사고는 Tailwind 와 번들러가 있어야 재현된다. `README.md` 의 새 예시(`@layer theme, base, ns-controls, components, utilities;` 가 맨 위, 두 CSS 임포트가 그 아래, `globals.css` 한 파일)를 **그대로** 따라 구성하고 확인한다.

```js
getComputedStyle(document.querySelector(".ns-button--outline")).borderTopWidth
// "1px" 이어야 한다. "0px" 이면 preflight 가 이긴 것이다.
```

**경고도 에러도 없다.** 눈으로 테두리를 찾는 것보다 위 한 줄이 확실하다. `.ns-*` 가 전부 같은 `@layer ns-controls` 안에 있으므로 이 한 줄이 갤러리 이관이 넣은 새 클래스(`.ns-chip`·`.ns-accordion`·`.ns-message` 등)까지 함께 판정한다.

### B-4. React `Card` 의 머리-본문 (0.2.5 설계 §5)

`docs/consumer-example.tsx` 는 프롭 **타입만** 검사하고 아무것도 렌더하지 않는다. `index.html` 에는 React 가 없다. 따라서 **클래스 이름을 틀리게 적거나 중첩을 틀리게 짜도 `npm run check` 가 통과하고 `index.html` 에서도 영영 안 드러난다.**

개발자 도구로 클래스 이름을 직접 대조한다. `src/react/controls/Card.tsx` 가 `heading` 을 받았을 때 내야 하는 것은 이것이다.

```
.ns-card
├─ .ns-card__header
│  ├─ div                        (이름 없는 감싸개)
│  │  ├─ h2|h3.ns-card__title
│  │  └─ p.ns-card__description  (description 을 줬을 때만)
│  └─ .ns-card__actions          (actions 를 줬을 때만)
└─ .ns-card__body
```

- 이름 없는 감싸개 `<div>` 가 실제로 그려지는지 — 빠지면 `.ns-card__header` 의 `justify-content: space-between` 이 설명을 오른쪽 끝으로 민다
- `headingLevel` 이 `2`(기본)와 `3` 에서 각각 `<h2>`/`<h3>` 를 내는지
- **`heading` 없이 쓴 기존 호출부의 출력이 예전과 완전히 같은지** — `.ns-card` 하나에 자식이 그대로 들어간 모양이어야 한다. 이것이 "기존 소비자가 안 바뀐다" 는 약속의 본체다
- **클래스가 실제로 이기는지.** `.ns-card__title` 은 이 라이브러리가 **제목 요소에 붙이는 첫 클래스**다. 소비자 `globals.css` 에 레이어 없는 `h2 { … }` 가 있으면 그것이 `@layer ns-controls` 를 특정도와 무관하게 이긴다 — **에러도 경고도 없이 제목만 다르게 그려진다.** 위 세 항목은 이름과 중첩만 보므로 이것을 잡지 못한다. `getComputedStyle(...).fontSize` 가 `--ns-font-size-base` 값인지 본다. 이긴다면 그 규칙을 레이어에 넣거나 카드 제목을 선택자에서 뺀다(`index.html` 의 `.ns-card` 주의 참고)

### B-5. `ns-tabs` — 하이드레이션 전 활성 탭 표시 (갤러리 이관)

`active` 는 프로퍼티 전용이고 `@lit/react` 의 `createComponent` 는 반응형 프로퍼티를 `useLayoutEffect` 에서만 설정한다. 그래서 **서버 마크업에 `aria-selected` 가 실리지 않고, 밑줄이 그 속성에 걸려 있어 첫 페인트에는 모든 탭이 선택되지 않은 모양으로 나온다.** 이것은 `index.html` 의 `ns-tabs` 주의에 문서화돼 있지만, **연역이지 관측이 아니다** — 실제로 서버 마크업을 뽑아 본 사람이 아직 없다.

- Next.js 페이지 소스 보기(JS 비활성 상태)에서 탭 버튼에 `aria-selected` 가 **없는지**
- 하이드레이션 후 밑줄이 붙는지, 그 사이 깜빡임이 받아들일 만한지
- 패널 쪽 `hidden` 은 소비자가 직접 렌더하므로 **서버에서도 맞아야 한다** — 첫 페인트에 패널이 전부 보이면 그건 소비자 코드 문제다

**판단이 필요한 항목이다.** 깜빡임이 거슬리면 `ns-sidebar` 가 쓴 것과 같은 해법(shim 이 `data-ns-*` 를 함께 렌더)이 자리이고, 그것은 라이브러리 변경이라 이번 델타 밖이다.

## A. 이 저장소의 `index.html` 에서 확인한다

`npm run demo` 로 빌드하고 연다(릴리스 직후에는 `dist/` 가 사라지므로 다시 빌드해야 한다). **개발자 도구를 열어 둔 채로 본다** — A-11 · A-15 는 콘솔 경고가 판정 근거다.

### A-1. 표 선택 (0.2.5 설계 §1)

`#table-select-demo` · `#table-both-demo` 에서 본다.

- 행 체크박스를 눌러 선택·해제가 되는지, 체크박스에 포커스를 두고 **Space** 로도 같은지
- 전체 선택 체크박스가 3-상태를 보이는지 — 행이 일부만 선택되면 indeterminate(가로줄), 전부면 체크, 하나도 없으면 빈 칸
- 전체 선택을 누르면 행 전부가 그 값을 따라가는지
- **체크박스 네모 바깥의 라벨 영역**을 눌러도 토글이 **한 번만** 일어나는지

마지막 항목은 누를 자리를 찾기가 어렵다. 표 데모의 `.ns-checkbox` 에는 글자(`<span>`)가 없지만, 그 라벨은 `display: flex` 라 셀 폭을 채우고 `padding: var(--ns-space-1-5) 0` 을 갖는다 — **체크박스 오른쪽의 빈 자리와 위아래 여백**이 라벨만 있는 클릭 영역이다.

**잘못된 것:** 그 자리를 한 번 눌렀는데 체크가 켜졌다 꺼진다(같은 클릭이 두 번 처리됐다는 뜻). 정상이면 한 번만 토글된다.

### A-2. `aria-sort` (0.2.5 설계 §2)

**`#sort-demo` 에서 본다** — `ns-table` 이 `aria-sort` 의 유일한 작성자인 데모이고, 처음에는 어느 칼럼도 정렬돼 있지 않다.

**`#table-sort-states-demo` 로는 이 항목을 확인할 수 없다.** 그 표는 `ns-table` 로 감싸지 않고 `aria-sort` 를 마크업에 손으로 써 둔 정적 예시다(감싸면 컴포넌트가 손으로 쓴 값을 덮어쓰므로 일부러 그렇게 돼 있다).

- 개발자 도구로 **정렬 훅이 붙은 `th[data-ns-sort-key]`**(이름 · 가입일)를 보면 정렬 전에 `aria-sort` 가 **아예 없는지** (`"none"` 이 아니라 부재). **훅이 없는 부서 칼럼을 보면 안 된다** — 컴포넌트가 애초에 손대지 않는 `th` 라 통과가 공허하다
- 정렬하면 `ascending`/`descending` 이 붙고, 같은 칼럼을 3-상태 한 바퀴 돌려 해제하면 **다시 사라지는지**
- 정렬되지 않은 칼럼에서도 삼각형이 `opacity: 0` 으로 **자리를 지켜 헤더 폭이 흔들리지 않는지** (`#table-sort-states-demo` 가 이 항목의 정적 대조본이다 — 세 상태가 한 줄에 나란히 있다)

> **먼저 읽을 것 — 헤더 행이 이 델타에서 약 4px 낮아진다. 회귀가 아니다.**
>
> 원인은 A-3 의 `th` 줄높이 변화(`1.25rem` → `1rem`)이고 **`aria-sort` 작업과 무관한 부수효과**다. `.ns-table__sort` 는 `font: inherit` 라 그 줄높이를 그대로 물려받으므로, **정렬 버튼이 라벨과 삼각형을 통째로 데리고 4px 만큼 짧아지고 그만큼 위치가 옮겨간다.**
>
> **삼각형이 자기 라벨을 기준으로 움직이지는 않는다.** `.ns-table__sort` 는 `inline-flex` 이고 아이템이 둘이다 — 라벨 글자를 감싸는 익명 플렉스 아이템(높이 = 줄높이)과 `::after`(테두리로 그린 `.5rem × .3rem` 상자). 교차축 크기는 둘 중 큰 쪽이라 곧 줄높이이고, `align-items: center` 가 라벨과 삼각형을 **같은 중심선**에 맞춘다. 둘의 상대 위치는 불변이다.
>
> 그러니 **삼각형만 따로 보지 말고 헤더 행 전체의 높이를 본다.** 삼각형을 자기 라벨과 대조하면 아무 차이도 안 보이고, 그러면 이 경고가 틀렸다고 결론 내리게 된다 — 이 경고가 막으려는 것과 정확히 반대다.

### A-3. 문서 페이지 표 규칙에 가드가 붙었다 — 표 데모 일곱 개 전부

`index.html` 의 `<style>` 은 레이어에 들지 않고 `dist/controls.css` 는 `@layer ns-controls` 라, 이 페이지의 `table`/`th`/`td` 규칙이 특정도와 무관하게 `.ns-table` 을 이기고 있었다. `:not(:where(.demo *, ns-dialog *))` 를 붙이면서 아래 **일곱 가지**가 동시에 바뀐다. 전부 "라이브러리가 원래 그리려던 모양" 으로 돌아가는 것이라, **다르게 보이는 것 자체는 정상이다.**

| 무엇 | 전 (페이지 규칙이 이김) | 후 (`.ns-table` 이 그림) |
|---|---|---|
| **마지막 행 구분선** | **그어져 있었다** | 없다 (`tbody tr:last-child td { border-bottom: 0 }`) |
| `td` 세로 정렬 | `top` | `middle` |
| `th` 세로 정렬 | `top` | `middle` (UA 기본값으로 복귀) |
| `td` 글자 크기 | `xs` (.75rem) | `sm` (.875rem, `.ns-table` 에서 상속) |
| `th` 줄높이 | `sm` (1.25rem) | `xs` (1rem) — **헤더 행이 약 4px 낮아진다** |
| `td` 패딩 | `space-2 space-3` | `space-3` (사방) — **세로만 늘어난다.** 가로는 양쪽 다 `space-3` 이라 폭에 기여하지 않는다 |
| `<table>` 바깥 여백 | `space-4 0` | 없음 — 데모 패널 안에서 위아래로 붙는다 |

`th` 의 글자 크기·패딩·색·굵기·아래 테두리·좌측 정렬은 양쪽이 같은 값이라 **바뀌지 않는다.** `td` 줄높이도 양쪽 다 `1.25rem` 이라 그대로다.

대상 데모는 `.demo` 안에 `.ns-table` 이 있는 **일곱** 개이고 그것이 전부다: `#table-demo` · `#table-narrow-demo` · `#table-sort-states-demo` · `#table-row-click-demo` · `#sort-demo` · `#table-select-demo` · `#table-both-demo`.

**특히 볼 데모는 넷이고, 이유는 셋이다.**

- **`#table-select-demo` · `#table-both-demo`** — `th` 세로 정렬 변화가 눈에 보이는 유일한 두 곳이다. 이 두 데모의 헤더 행만 `<th>` 안에 `.ns-checkbox` 라벨(약 `1.75rem`)과 평범한 글자 `th` 를 섞어 놓아서, 글자 헤더들이 **위 정렬에서 세로 가운데 정렬로** 몇 px 옮겨간다. **A-1 의 선택 동작 확인도 같은 데모에서 하므로 한 번에 본다.**
- **`#table-sort-states-demo`** — 헤더 행이 4px 낮아지면서 정렬 버튼이 라벨·삼각형을 통째로 데리고 움직인다. 오독을 막는 설명은 **A-2 의 인용 블록**에 있다.
- **`#table-narrow-demo`** — 표에서 **`td` 세로 정렬** 줄이 눈에 보이는 곳이다. 그 행의 액션 칸에는 `.ns-button--sm`(`min-height: 1.75rem`)이 셋 들어 있고 나머지 칸은 글자 한 줄(`1.25rem`)이라, 행 높이를 버튼이 정한다. `top` → `middle` 로 바뀌면 **글자 칸의 내용이 약 4px 내려온다.**

**`#table-narrow-demo` 가 위험 지점이 아니라는 것은 가로 스크롤에 대해서만 참이다.** 7 칼럼에 전체 URL 한 칸과 버튼 세 개짜리 액션 칸이 들어 있고 컨테이너는 `max-width: 26rem` 이라, `min-width: max-content` 가 이미 컨테이너를 한참 넘는다. 폭을 바꾸는 것은 `td` 글자 크기(`xs`→`sm`) **하나뿐이고**(패딩 변화는 세로 전용이다) 그것도 넓히는 방향이라 **가로 스크롤은 사라질 수 없다.** 세로 정렬은 별개이고, 위에 적었듯 여기가 그것을 보는 자리다.

`code` 규칙에는 가드를 붙이지 않았으므로 **`code` 로 바뀌는 화면은 없다.** `#tokens` 절의 스와치 라벨 19 개는 그대로다 — 붙이지 않기로 한 기준과 그 19 개의 출처(마크업이 아니라 배선 스크립트)는 `index.html` 의 `<style>` 주석에 적혀 있다.

### A-4. `.ns-card` 머리-본문 (0.2.5 설계 §5)

- `#card-demo`(머리 없음)와 `#card-header-demo`(머리 있음)를 나란히 놓고 **머리 없는 쪽의 패딩이 예전 그대로인지**
- 구분선이 카드 폭 전체가 아니라 **내용 폭까지만** 그어지는지. 전체 폭으로 긋지 않는 것은 의도다 — `--ns-card-padding` 이 `.ns-card` 자신에게 있어서, 전체 폭으로 그으려면 그 패딩을 `__header`·`__body` 로 내려야 하고 그러면 머리 없이 쓰던 기존 호출부의 패딩이 경고 없이 사라진다
- 제목이 길 때 액션이 찌그러지거나 줄바꿈되지 않는지 (`.ns-card__actions` 가 `flex-shrink: 0`). **데모의 제목은 "최근 주문" 이라 그대로는 안 보인다** — 개발자 도구에서 `.ns-card__title` 의 글자를 길게 바꿔 놓고 본다
- 다크모드에서 같은지

### A-5. 명령형 대화상자의 본문 크기

`#confirm-demo` 의 세 버튼(`nsAlert` · `nsConfirm` · `nsConfirm (danger)`)이 띄우는 대화상자의 **본문 글자가 커진다** — 이 페이지의 `p` 규칙(`sm` · 1.7)을 받던 것이 가드 목록의 `ns-dialog *` 때문에 이제 대화상자에서 상속받는다(브라우저 기본 16px · `normal`). 확인할 것은 하나다.

> `#dialog-demo` 의 대화상자를 열어 본문을 보고, 이어서 `#confirm-demo` 의 대화상자를 열어 본문을 본다. **두 본문의 크기가 같아야 한다.** 지금까지 달랐다.

색은 안 바뀐다 — `ns-dialog` 의 shadow 가 `<dialog>` 에 `--ns-color-fg-body` 를 이미 세운다.

줄높이는 1.7 → `normal` 이라 **여러 줄 메시지에서 줄 간격이 좁아 보일 수 있다.** 좁아서 읽기 나쁘면 고칠 자리는 이 페이지가 아니라 `ns-dialog` 의 `.body` 다(지금 `.body` 는 글자 크기도 줄높이도 정하지 않는다). 라이브러리 변경이므로 이번 델타에서 하지 않았다.

### A-6. 아코디언 데모의 "커 보이는 본문" — 결함이 아니다

`p` 가드가 붙은 뒤로, `#accordion-demo` 의 본문 채움 글(`<p style="margin:0">닫힌 채로 시작한다.</p>` 등 셋)이 **아코디언 자신의 제목보다 크게** 렌더된다. `.ns-accordion__title` 은 `--ns-font-size-sm`(0.875rem)인데 본문 `<p>` 는 이제 아무 규칙도 안 받아 `body` 에서 상속받은 16px 이기 때문이다.

**셋 다 접힌 `<details>` 안에 있다. 열어야 보인다.** 처음부터 열려 있는 둘째 항목("권한")에는 `<p>` 가 없고 체크박스만 있어서, 페이지를 연 상태로는 이 변화가 **한 글자도 보이지 않는다.**

**버그가 아니다.** 스타일 없는 `<p>` 가 소비자 페이지에서 갖는 값이 정확히 그것이고, 아코디언 본문 타이포그래피는 라이브러리가 정하지 않는다(`.ns-accordion__body` 는 레이아웃만 준다). 하지만 **읽는 사람이 결함으로 오인할 가장 유력한 한 곳**이라 미리 적어 둔다.

데모로서 어색하다고 판단되면 고칠 자리는 **데모 마크업**(그 `<p>` 에 실제 소비자가 쓸 법한 클래스를 주는 것)이지 페이지 `<style>` 이 아니다. 가드를 되돌리면 A-3 이 고친 것이 함께 되돌아간다.

**같은 가드가 모든 데모의 꾸미지 않은 `<p>` 에 걸린다** — `#card-demo`·`#card-header-demo` 의 채움 글도 커진다. 반대로 라이브러리 클래스를 가진 산문(`.ns-card__description` · `.ns-message p` · `.ns-multi-select__empty`)은 페이지 규칙 대신 자기 클래스의 크기·색을 보이게 된다. 아코디언은 그중 **차이가 가장 눈에 띄는 곳**일 뿐이고, 나머지도 판정 기준은 같다: 데모가 라이브러리가 그리는 모양을 보여주게 된 것이 이 변화의 목적이다.

아래 A-7 부터는 **처음 그려지는 것을 보는** 항목이다. 위쪽이 "바뀐 것이 의도한 대로 바뀌었나" 를 묻는 반면, 여기서는 대조할 이전 모양이 아예 없다 — 컴포넌트와 클래스가 통째로 새로 들어왔기 때문이고(갤러리 이관 · 오버레이 사이클), 그래서 판정 기준을 항목마다 따로 적었다.

### A-10. `.ns-message`

`#message-demo`. 보는 것은 하나다 — **한 줄 메시지가 8rem 짜리 상자의 세로·가로 가운데에 있는지.**

이 클래스가 하는 일이 그것뿐이다. `flex: 1 1 0%` 로 남는 자리를 통째로 차지하고 그 안에서 가운데 정렬한다. **그래서 부모가 flex 컨테이너여야 한다** — 아니면 남는 자리를 차지하라는 선언이 아무 데도 걸리지 않는다.

**잘못된 것 둘을 구분한다.**

- **가로는 가운데인데 세로로 위에 붙어 있으면 부모가 flex 가 아니다.** `flex: 1 1 0%` 가 무시돼 높이가 내용만큼만 잡히고, 상자 아래쪽이 빈 채로 남는다.
- **왼쪽 위에 그냥 놓여 있으면 `.ns-message` 자신의 규칙이 안 걸린 것이다.** 클래스 이름이 틀렸거나 캐스케이드에서 졌다는 뜻이고, 원인이 완전히 다르다.

> **`#message-demo` 에 `block` 이 없는 것은 의도다.** 이 페이지의 데모 34 개 중 31 개가 `class="demo block"` 이고, `class="demo"` 로 남은 셋 중 하나가 여기다(나머지 둘은 사이드바와 전체 셸 데모라 역시 flex 배치가 필요하다). `.demo` 는 `display: flex` 이고 `.demo.block` 이 그것을 `display: block` 으로 되돌리므로, **`block` 을 붙이는 순간 이 클래스의 유일한 전제가 사라지고 데모가 자기가 보여주려는 것을 못 보여주게 된다.** 정렬이 어긋나 보인다고 `block` 을 더해 "고치지" 않는다 — 그 어긋남이 바로 위 첫 번째 실패 모양이다.

`.ns-message p` 의 색(`--ns-color-fg-subtle`)이 페이지 산문과 다르게 보이는 것은 A-6 이 설명하는 가드의 결과이고 정상이다.

### A-11. `ns-tabs`

`#tabs-demo`. 이 항목은 **콘솔이 있어야 끝까지 간다.**

클릭·키보드로 닿는 것:

- 좌우 화살표 이동 · `Home`/`End`
- 탭이 넘칠 때 가로 스크롤이 생기는지, 포커스 링이 잘리지 않는지
- **활성 밑줄이 선택할 때 1px 튀지 않는지**
- 탭 스타일이 전과 같은지. 선택자가 `ns-tabs button` 에서 `ns-tabs [data-ns-tab]` 으로 바뀌어 특정도가 `(0,0,2)` → `(0,1,1)` 로 올라갔다. 데모의 모든 탭 버튼이 `data-ns-tab` 을 갖는 것은 정적으로 확인됐지만, **그려지는 모양이 같은지는 눈으로만 판정된다**

**콘솔 ① — 제어 모드에서 소비자가 이벤트를 무시하는 경로.** 데모는 비제어로 배선돼 있어 클릭으로는 도달할 수 없다.

```js
const tabs = document.querySelector("#tabs-demo ns-tabs");
tabs.addEventListener("ns-tab-change", (e) => console.log("요청됨:", e.detail.id));
tabs.active = "live";   // 제어 모드. 이후 active 를 갱신하지 않는다 = 무시
// "운영 중" 에 포커스를 두고 → 를 세 번 누른다.
//   기대: 콘솔에 요청이 세 번 찍히고, 포커스는 신청 → 문의 → 운영 중 으로 계속 돌며,
//         aria-selected="true" 는 "운영 중" 에 그대로 있다.
// 되돌리기: tabs.active = undefined;
```

**포커스가 한 칸 옆에 갇히면 회귀다** — 화살표 기준점을 선택 탭이 아니라 포커스 탭으로 잡은 이유가 이것이다. 이 상태에서 **패널과 탭 표시가 어긋나 보이는 것은 정상이다**(데모의 패널 전환 배선이 `ns-tab-change` 를 그대로 듣기 때문이고, 소비자가 이벤트를 반만 처리한 상태를 흉내 낸 것이다).

**콘솔 ② — 목록에 없는 활성 탭의 경고.** 조용한 죽은 클릭을 막으려고 넣은 경고이고, 이 저장소에는 러너가 없어 **아직 한 번도 실행돼 본 적이 없다.**

```js
const tabs = document.querySelector("#tabs-demo ns-tabs");
tabs.active = "typo";
//   기대: [ns-tabs] active="typo" 와 일치하는 data-ns-tab 이 없습니다 … 경고가 한 번 뜬다.
//         첫 번째 탭이 선택된 채로 그려지고, 그 탭을 눌러도 ns-tab-change 가 나가지 않는다.
// 되돌리기: tabs.active = undefined;
```

경고가 **한 번만** 떠야 한다(`#warnedNoMatch` 가 반복을 막는다).

### A-12. 행 클릭 데모 — 누적 횟수

`#table-row-click-demo` 와 그 아래 `#table-row-click-log`.

- `Tab` 으로 이름 버튼(`.ns-table__row-button`)에 닿는지, 포커스 링이 셀 경계에서 끊기지 않는지
- **로그 줄의 누적 횟수가 마우스 클릭 한 번 · 버튼 위의 `Enter` 한 번 · `Space` 한 번에 각각 1 씩만 오르는지.** **2 씩 오르면 이중 발화다** — 핸들러가 `<tr>` 에만 있어야 하는 이유가 그것이고, 이 패턴이 존재하는 이유가 그 버그다
- 세 예시가 `<ns-table>` 로 감싸여 가로 스크롤 컨테이너를 갖는다. `.demo` 가 넘치는 부분을 잘라내므로 **차이가 잘 드러나지 않는다** — 개발자 도구에서 셀 하나에 긴 문자열을 넣어 `ns-table` 안에서만 스크롤이 생기는지(페이지 전체가 밀리지 않는지) 본다

### A-13. `ns-multi-select`

`#multi-select-demo`. 클릭으로 닿는 것:

- 검색이 라벨뿐 아니라 **`meta`(부서명)에도 걸리는지**
- 칩이 **고른 순서**로 남는지, 목록이 넘칠 때 스크롤되는지
- 검색 결과가 없을 때 `empty-message` 가 뜨는지

**콘솔 ① — 제어 모드에서 소비자가 이벤트를 거절하는 경로.**

```js
const ms = document.querySelector("#multi-select-demo ns-multi-select");
ms.addEventListener("ns-multi-select-change", (e) => console.log("요청됨:", e.detail.values));
ms.value = ["kim", "park"];   // 제어 모드로 들어간다. 이후 value 를 갱신하지 않는다 = 거절
// 이제 목록에서 아무 체크박스나 누른다.
//   기대: 콘솔에 "요청됨: [...]" 이 찍히고, 체크박스는 눌린 직후 원래 상태로 돌아오며,
//         칩 줄은 김담당·박승인 그대로다.
```

**되돌아가지 않으면 화면만 체크된 채 영구히 어긋난다.**

**콘솔 ② — 늦은 `defaultValue` 대입.** 첫 렌더가 지난 뒤에 대입해도 반영되는지(`hasUpdated` 가드에 걸려 조용히 버려지지 않는지).

```js
const ms = document.querySelector("#multi-select-demo ns-multi-select");
ms.value = undefined;                  // 비제어로 되돌린다
ms.defaultValue = ["choi", "han"];     // 페이지 로드가 끝난 뒤의 대입
//   기대: 칩 줄이 최데이터·한지우로 바뀐다.
```

**아직 한 번도 체크박스를 토글하지 않았을 때만** 그렇다. 토글한 뒤에는 내부 상태가 생겨 `defaultValue` 가 더 이상 보이지 않는 것이 **정상 동작이다.** 이미 토글했다면 새로 고치고 다시 한다.

### A-14. `nsToast`

`#toast-demo` 의 tone·duration 버튼 여섯(기본 · success · danger · warn · `duration=1500 (1.5초 뒤 사라짐)` · `duration=0 (안 사라짐)`). 같은 데모의 위치 버튼 넷은 A-16 에서 따로 본다.

- 여러 개가 쌓였을 때 겹치지 않는지
- **마우스를 올리면 멈추는지, `Tab` 으로 닫기 버튼에 포커스를 줘도 멈추는지.** 정지 사유가 hover 와 포커스로 따로 추적되므로, 하나를 풀어도 다른 하나가 살아 있으면 계속 멈춰 있어야 한다
- `duration=0` 이 저절로 사라지지 않는지, 닫기 버튼으로 닫히는지
- **`duration=1500` 이 눌린 뒤 대략 1.5 초에 저절로 사라지는지.** 이 버튼은 이번 사이클에 새로 생겼고, 있는 이유는 `duration` 이 "자동 소멸을 끄는 스위치" 가 아니라 "머무는 시간" 이라는 것을 눈으로 보이게 하는 것이다. **잘못된 것:** 사라지지 않거나(0 처럼 굳었다), 누르자마자 사라진다(타이머가 남은 시간 0 으로 걸렸다는 뜻이고 `#startItem`·`#pauseTimers` 회귀의 증상이다)

**tone 표시가 왼쪽 색 띠에서 메시지 앞의 작은 점으로 바뀌었다.** 이 델타에서 가장 눈에 띄는 변화이고, 아래 넷이 판정 항목이다. 예전 모양(`border-left: 3px`, neutral 은 `--ns-color-line` 으로 같은 두께)은 더 이상 없다 — **왼쪽 변이 두꺼워 보이면 그것이 회귀다.**

- **네 tone 을 한꺼번에 띄워 놓고 본다.** success·danger·warn 은 메시지 글자 앞에 자기 색 점 하나를 갖고, **`기본`(neutral)은 점이 아예 없다.** 점 지름은 `--ns-space-2`(0.5rem)이고 글자와의 사이는 `.toast` 의 `gap`(`--ns-space-3`)이다. **잘못된 것:** neutral 자리에 회색이든 투명이든 **무언가가 자리를 차지하고 있다** — 그러면 "없으면 그리지 않는다" 가 지켜지지 않은 것이다
- **neutral 의 글자 시작점이 색 있는 것보다 왼쪽인 것은 정상이다.** 섞어 쌓으면 글자 왼쪽 끝이 (점 + gap = 1.25rem) 만큼 어긋나 보인다. **의도한 선택이고 결함이 아니다** — 투명한 자리 채우기를 두지 않기로 한 결과다. 정렬을 맞추려고 스페이서를 넣지 않는다. 어긋남이 실제로 거슬리는지에 대한 **판단만** 남긴다(거슬린다면 그때 되돌릴 자리는 `ns-toast.styles.ts` 의 `.dot` 이다)
- **점이 첫 줄 글자의 세로 중앙에 있는지.** 긴 메시지로 두 줄 이상 만들어 본다 — 개발자 도구에서 `.message` 의 글자를 늘리는 것이 가장 빠르다. **잘못된 것:** 점이 상자 맨 위에 붙어 첫 글자보다 **위로** 뜬다. `.toast` 가 `align-items: flex-start` 라 `.dot` 의 `margin-top` 이 없으면 정확히 그렇게 된다
- **보조기술이 점을 읽지 않는지.** 점은 `aria-hidden="true"` 인 빈 `<span>` 이라 원래 읽을 내용이 없다. 스크린리더로 확인한다면 판정은 하나다 — **danger 토스트가 메시지 글자만 즉시 읽히고, 점에 해당하는 무의미한 발화("빈 항목" 등)가 끼지 않는다**

**콘솔 — 열린 모달을 이길 수 없다는 것.** `ns-dialog` 는 `showModal()` 로 열려 배경이 inert 이므로, 대화상자를 연 뒤에는 토스트 버튼을 **누를 수 없다.** 순서를 뒤집으면 클릭만으로 된다.

```
1. #toast-demo 에서 duration=0 을 눌러 토스트를 띄운다
2. 그대로 ns-dialog 절로 가서 "열기" 를 누른다
   기대: 토스트가 backdrop 뒤로 가려지고 닫기 버튼도 눌리지 않는다
3. 대화상자를 닫으면 토스트가 다시 보이고 다시 눌린다
```

대화상자가 열린 상태에서 새로 띄우려면 콘솔로만 가능하다: `NsCommonUi.nsToast("모달 뒤에 가려진다")` → **아무것도 보이지 않고**, 대화상자를 닫으면 그때 드러난다.

**이것은 버그가 아니라 문서화된 한계다** — top layer 는 정수 `z-index` 로 닿는 곳이 아니다.

### A-15. `nsAlert` · `nsConfirm` — 초기 포커스와 포커스 복귀

`#confirm-demo` 의 세 버튼. **개발자 도구를 열어 둔 채로 한다.**

**`nsConfirm (danger)` 에서 셋을 본다.**

1. **열리자마자 포커스가 "취소" 에 있다.** 링이 취소 버튼에 보여야 한다. "삭제" 에 있으면 회귀다
2. **연 직후 곧바로 `Enter` 를 누르면 `false` 로 풀린다.** 로그 줄이 `danger confirm → false` 여야 한다. `true` 면 초기 포커스가 파괴적 버튼에 갔다는 뜻이다
3. **콘솔이 깨끗해야 한다.** `[ns-confirm] 취소 버튼에 초기 포커스를 주지 못했습니다…` 경고가 보이면 **화면상 포커스가 맞아 보여도** 초기 포커스 메커니즘이 회귀한 것이다

`ESC` 와 backdrop 클릭이 `false` 인지도 같은 자리에서 본다.

**포커스 복귀 — 닫힘 경로 다섯 전부.** `nsAlert`·`nsConfirm` 모두. 닫은 뒤 **포커스가 대화상자를 연 그 버튼으로 돌아와야 한다.** `<body>` 로 떨어지면 다음 `Tab` 이 문서 맨 위에서 다시 시작한다.

| # | 닫는 방법 |
|---|---|
| 1 | 확인 버튼 |
| 2 | 취소 버튼 |
| 3 | `ESC` |
| 4 | backdrop 클릭 |
| 5 | 헤더의 닫기(×) 버튼 |

닫은 직후 `Tab` 을 한 번 눌러 **여는 버튼의 바로 다음 요소로 가는지**로 판정하는 것이 가장 확실하다. 콘솔에서 `document.activeElement` 를 봐도 된다.

### A-16. 토스트 네 자리 (토스트 위치 설계 §1 · §3)

`#toast-demo` 의 위치 버튼 넷. 누르면 `nsToastPosition()` 을 부른 뒤 그 자리에 토스트를 하나 띄운다.

**이 기능은 정적으로 거의 확인되지 않는다.** 위치는 렌더 결과이고 `npm run check` 는 CSS 규칙이 존재한다는 것조차 보지 않는다 — 이 항목이 유일한 증거다.

- 네 버튼이 각각 **자기 이름이 말하는 자리**에 띄우는지. 이름은 `세로-가로` 다 (`top-right` = 위 오른쪽)
- **가운데 두 자리가 진짜 화면 가로 중앙인지.** 네 규칙이 인셋 넷을 모두 적는 이유가 이것이다 — 한 규칙이 남긴 값이 지워지지 않으면 `left` 와 `right` 가 함께 걸려 **가운데가 아니라 오른쪽으로 밀린 자리**에 뜬다. 눈으로는 "조금 오른쪽" 으로만 보이므로 창 가운데와 대조한다
- **창을 400px 이하로 좁히고 가운데 자리를 다시 본다.** 토스트 폭이 화면의 절반쯤으로 눌리면 회귀다 — `:host` 의 `width: max-content` 가 막는 것이 정확히 그 증상이고, 없으면 `left: 50%` 짜리 fixed 상자의 shrink-to-fit 이 `50vw` 에서 잘린다. 정상이면 양옆에 `1rem` 씩 남기고 화면을 거의 채운다
- **`duration=0` 을 먼저 띄워 두고 위치를 바꾼다.** 떠 있던 토스트가 **함께 새 자리로 옮겨가야 한다.** 리전이 문서당 하나라는 사실의 관측 가능한 결과이고, 문서에도 그렇게 적혀 있다 — **버그가 아니다**
- 여러 개를 쌓아 본다. 상단 두 자리는 리전이 아래로 자라고 하단 두 자리는 위로 자라며, **양쪽 모두 새 것이 아래**여야 한다 (`column-reverse` 를 쓰지 않은 근거)
- **토스트가 가리는 자리 바깥의 클릭이 여전히 되는지.** `:host` 가 `pointer-events: none` 이고 `.toast` 항목만 `auto` 로 되살린다. 기본 자리가 화면 위 가운데로 옮겨오면서 **가려지는 대상이 바뀌었다** — 예전에는 우하단 여백이었고 지금은 본문 한가운데 위쪽이다. 토스트를 띄워 둔 채로 그 근처(토스트 좌우와 바로 아래)의 링크·버튼을 눌러 본다. 안 눌리면 리전이 클릭을 가로챈 것이다

**설정이 새로고침에 남지 않는 것은 정상이다.** 모듈 변수 하나이고 저장소를 쓰지 않는다. 새로 고치면 기본값 `top-center` 로 돌아온다.

### A-17. 첫 프레임에 엉뚱한 자리로 뜨지 않는지 (토스트 위치 설계 §3)

**연역만 있고 관측이 없는 항목이다.** 저장소 안의 근거는 셋 다 코드 읽기다 — ① Lit 이 속성 반영을 shadow DOM 커밋보다 먼저 한다, ② 그 전 구간에는 shadow 가 비어 있어 그릴 것이 없다, ③ 그래도 `:host` 에 기본 자리의 인셋을 뒀다. 셋 다 맞아도 화면이 다르게 나올 가능성은 사람만 지울 수 있다.

**페이지를 새로 고친 직후**(리전이 아직 없는 상태) `#toast-demo` 의 "기본" 을 누른다.

- 토스트가 **처음부터 상단 중앙**에 나타나야 한다
- **잘못된 것:** 한 프레임 다른 자리(문서 맨 아래 · 왼쪽 위 · 우하단)에 나타났다가 제자리로 튀어 오른다

한 프레임은 눈으로 놓치기 쉽다. 확실히 보려면 개발자 도구에서 **CPU 를 4× 이상 느리게** 걸고 다시 누르거나, Performance 녹화의 스크린샷 프레임을 넘겨 본다.

**두 번째 이후 클릭으로는 이 항목을 확인할 수 없다.** 리전은 문서당 하나라 이미 자리를 잡은 뒤이고, 확인 대상인 "생성~첫 업데이트" 구간이 존재하지 않는다. 다시 보려면 새로 고친다.

**위치 버튼으로는 이 항목을 대신할 수 없다.** 그때는 리전이 이미 있고 속성도 이미 붙어 있어서 확인 대상 구간 자체가 없다 — 보이는 것은 리전이 옮겨가는 것이지 첫 프레임이 아니다.

### A-18. 다크모드 — 위 전부를 한 번 더

페이지 위의 `data-theme` 토글로 뒤집고 A-1 부터 다시 훑는다. **새로 들어온 것이 많은 델타라 이 항목이 특히 크다** — `.ns-chip` 의 토글 배경, `.ns-message`, `.ns-button--danger`, 토스트 tone 점, 탭 밑줄, 대화상자 backdrop 이 전부 처음으로 다크에서 그려진다.

**다크의 액센트 값 자체가 이 델타에서 바뀌었다. 그것은 A-19 에서 따로 본다** — 여기서 훑는 김에 함께 보되, 판정 기준은 A-19 에 있다.

### A-19. 다크 액센트가 낮아졌다 — 약 열다섯 곳이 함께 어두워진다

`--ns-color-accent` 의 **다크 절반만** `oklch(98.5% 0 0)` → `oklch(87.1% 0.006 286.286)` 로, `--ns-color-accent-hover` 가 `oklch(92% …)` → `oklch(70.5% 0.015 286.067)` 로 내려갔다. **밝은 모드는 한 글자도 바뀌지 않았다.**

바꾼 이유는 넓은 채움면이다. 98.5% 로 칠한 solid 버튼은 21% 표면 위에서 거의 흰 판이 되고, `--full` 처럼 폭을 꽉 채우면 액센트가 아니라 **광원**으로 읽힌다. 대비 수치로는 드러나지 않는 결함이라 눈으로만 판정된다.

**이 토큰을 읽는 곳이 약 열다섯이고 전부 함께 어두워진다. 그것이 의도다 — 개별 컴포넌트의 회귀가 아니다.** solid 버튼 배경, 포커스 링 넷(`controls.css` 두 곳 · `ns-toast` · `ns-dialog` · `ns-header`), 입력 포커스 테두리, 네이티브 체크박스·라디오의 `accent-color`, 탭 활성 밑줄과 `.ns-tabs__count` 배지, 선택된 `.ns-chip`, 활성 `ns-nav-item` 이다.

**다크모드로 두고** 본다. 판정 항목은 여섯이다.

- **`#button-demo` 의 solid 버튼과 `--full` 버튼이 더는 빛나 보이지 않는지.** 이 델타의 목적이 이 한 줄이다. **잘못된 것:** 여전히 눈에 먼저 들어오는 흰 판이다(값이 안 먹었다는 뜻이니 개발자 도구로 계산값을 본다), 또는 **반대로 표면과 구분이 안 될 만큼 가라앉아 "이것이 주 버튼" 으로 읽히지 않는다**
- **버튼 글자가 배경 위에서 읽히는지.** `--ns-color-accent-fg` 는 다크에서 `oklch(21%)` 이고 새 배경 위 대비는 계산상 **약 12:1** 이다(hover 70.5% 위에서도 약 6.9:1). 숫자로는 넉넉하므로 **읽기 어려워 보인다면 그것은 계산이 아니라 실제 렌더가 다르다는 신호다** — 그때는 개발자 도구로 두 색의 계산값을 직접 본다
- **hover 가 여전히 구분되는지.** solid 버튼에 마우스를 올리면 87.1% → 70.5% 로 **어두워져야 한다.** 밝은 모드(21% → 27.4%, 밝아짐)와 방향이 반대인 것은 원래 그랬고 이 델타가 바꾼 것이 아니다. **잘못된 것:** hover 와 기본 상태가 구분되지 않는다
- **포커스 링이 두 배경 모두에서 또렷한지 — 이 항목이 가장 중요하다.** 링이 사라지는 것은 버튼이 밝은 것보다 나쁜 결함이다. `Tab` 으로 훑으며 **`--ns-color-surface`(21%) 위**와 **`--ns-color-surface-sunken`(14.1%) 위** 둘 다에서 본다. 페이지 본문이 sunken 이고 카드·데모 패널·토스트·대화상자가 surface 다. 계산상 각각 **약 12:1 · 약 13:1** 로 비텍스트 기준 3:1 을 크게 넘는다. **잘못된 것:** 어느 한쪽에서 링이 배경에 묻혀 지금 어디에 포커스가 있는지 알 수 없다
- **`#checkbox-demo` 의 체크 표시가 보이는지.** 네이티브 `accent-color` 라 **체크 표시 색은 UA 가 정한다** — 배경이 밝으면 어두운 체크를, 어두우면 밝은 체크를 그린다. 87.1% 는 여전히 밝은 쪽이라 어두운 체크가 나와야 한다. **잘못된 것:** 체크한 상자가 그냥 밝은 사각형으로 보이고 체크 표시가 안 보인다(UA 가 경계값에서 밝은 체크를 골랐다는 뜻이고, 그러면 `accent-color` 만 별도 토큰으로 떼어낼 자리다). 라디오도 같이 본다
- **`#tabs-demo` 의 활성 밑줄과 `.ns-tabs__count` 배지, `#chip-demo` 의 선택된 칩, 사이드바의 활성 `ns-nav-item`.** 넷 다 "선택됨" 으로 계속 읽히는지만 본다. **잘못된 것:** 선택된 것과 안 된 것이 한눈에 구분되지 않는다

**마지막으로 밝은 모드로 되돌려 `#button-demo` 를 한 번 더 본다.** 밝은 모드가 조금이라도 달라졌으면 `light-dark()` 의 잘못된 절반을 고친 것이다.
