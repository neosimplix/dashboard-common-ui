# 릴리스 전에 사람이 봐야 하는 것

`.claude/rules/verification.md` 가 이 저장소의 회귀 확인 수단을 둘로 못박는다 — `npm run check` 와 `index.html` 육안 확인. 이 파일이 담는 것은 **두 범주**다.

- **A — `index.html` 육안 확인이 볼 목록.** 두 번째 수단은 볼 것의 목록이 있어야 작동한다.
- **B — 두 수단 **어느 쪽도** 닿지 않는 것.** `index.html` 에는 React 도 Tailwind 도 번들러도 없어서, 여기서는 재현 자체가 불가능하고 소비자 프로젝트가 있어야 확인된다. **B 는 `index.html` 확인의 일부가 아니라 세 번째 범주다.**

## 이 파일을 다루는 법

- **살아 있는 목록이다. 릴리스가 나가면 비운다.** 항목의 가치는 "바뀌었는데 아직 아무도 눈으로 안 봤다" 하나뿐이라, 확인이 끝난 항목은 소음이다. 낡은 항목이 쌓인 목록은 없는 것보다 나쁘다 — 훑고 넘기는 습관을 만들고, 그 습관은 다음 사이클의 진짜 새 항목까지 함께 넘긴다.
- **누적 로그로 만들지 않는다. 그 일은 git 이 이미 한다.** `git log -p docs/pending-human-checks.md` 가 사이클마다 무엇을 봐야 했는지를 그대로 준다. 파일 안에 이력을 또 쌓으면 중복이고, 둘이 어긋날 때 낡는 쪽은 언제나 파일 안이다.
- **비우는 법: 아래 `## 범위` · `## B` · `## A` 세 절을 통째로 지우고 `## 대기 없음` 한 줄을 남긴다.** `## 범위` 를 함께 지우는 것이 중요하다 — 그 절은 아래 목록이 무엇을 덮는지 설명하는 것이라, 목록 없이 남으면 없는 내용을 주장하는 문장이 된다. 파일 자체를 지우거나 완전히 비우지도 않는다. 그러면 "지금 정말 대기가 없다" 와 "아무도 안 채웠다" 가 구분되지 않는다.
- **비우는 시점은 태그를 자르기 전이다.** `.claude/skills/releasing/SKILL.md` 가 `## 실행` 앞에서 이 파일을 가리킨다. 남아 있는 항목은 확인되지 않은 항목이고, 태그는 되돌릴 수 없다.
- 항목을 더할 때는 **무엇을 보나** 와 **무엇이 잘못된 것인가** 를 함께 적는다. 하나만 있으면 보는 사람이 판정할 수 없고, 판정할 수 없으면 정상인 변화를 결함으로 신고하는 쪽으로 기운다. 아래 A 항목의 상당수는 그 오인을 미리 막으려고 있다.
- **B 를 A 보다 앞에 둔다.** A 는 `index.html` 을 열면 어차피 눈에 걸리지만, B 는 여기 적혀 있지 않으면 존재조차 알 수 없다.

## 범위

**`v0.4.0` 이후의 변경이다.** `v0.2.5..v0.4.0` 을 덮던 목록(B-1…B-5 · A-1…A-27)은 `v0.4.0` 이 나간 뒤 비웠다. 무엇이 있었는지는 `git log -p docs/pending-human-checks.md` 가 갖고 있다.

**이번 사이클 도중에 `ns-sidebar` 레일을 만들었다가 물렀다.** 레일을 전제로 세워 두었던 확인 항목(타일 정렬·타일 포커스 링·방향키·`data-ns-rail` 폴백·그룹 왕복 등)은 **판정할 대상이 없어져 전부 지웠다.** 지운 항목이 무엇이었는지는 `git log -p` 에 있고, 왜 물렀는지는 `docs/gotchas.md` 의 「레일을 만들었다가 물렀다」 에 있다. 살아 있지 않은 항목을 목록에 남기면 이 파일의 첫 규칙("낡은 항목이 쌓인 목록은 없는 것보다 나쁘다")을 스스로 어긴다.

이번 사이클이 넣은 것은 일곱이다.

- **문서 정리.** 소비자가 저자 한 사람뿐이라 태그별 이관 안내를 `README.md` 와 `index.html` 양쪽에서 걷어냈다. 이것만 있었다면 `dist/` 는 바뀌지 않았다.
- **Safari 전용 결함 하나.** 대화상자 본문이 WebKit 에서 높이 0 으로 붕괴해 한 줄짜리 문장에도 스크롤 막대가 생겼다. `.body` 를 `flex: 1` 에서 `flex: 1 1 auto` 로 바꿔 고쳤고, 근거는 `docs/gotchas.md` 에 있다. **`dist/` 가 바뀐다.**
- **세로 정렬 두 곳.** `ns-toast` 의 닫기 버튼이 첫 줄 글자와 세로 중심을 맞추고, `ns-dialog` 의 footer 가 우측이 아니라 가운데로 정렬한다. **후자는 배치의 자리를 옮긴 변경이라 파급이 넓다** — footer 슬롯에 들어온 것이 곧 flex 항목이어야 정렬과 `gap` 이 걸리므로, `confirm.ts` 와 `index.html` 데모가 버튼을 감싸던 `<div>` 를 걷어냈고 React `Dialog` shim 은 걷어낼 수 없는 래퍼에 `display: contents` 를 줬다. **`dist/` 가 바뀐다.**
- **`ns-nav-group` 그룹 접힘.** `collapsible` 을 쓴 그룹의 헤딩이 `div` 에서 `button` 이 되고 caret(`chevron-down`, 스프라이트에 새로 들어왔다)이 붙는다. React 래퍼에 토글 이벤트가 늘었다. **`dist/` 가 바뀐다.** **최상위 그룹에 써도 된다** — 레일 시절에는 "패널이 빈다" 는 이유로 하위 그룹에만 권했으나 그 이유가 사라졌고, 지금은 긴 목록을 줄이는 데 최상위가 가장 효과가 크다. `index.html` 의 좌측 문서 네비게이션이 그렇게 바뀌었다.
- **페이지네이션 폭 고정.** 페이지를 넘길 때마다 "이전"·"다음" 이 움직이던 것을 고쳤다. 슬롯 수를 현재 페이지와 무관하게 고정하고, 번호 칸을 균등 그리드로 묶었다. `page-window` 속성이 새로 생겼고 **DOM 에 래퍼 `<span class="ns-pagination-pages">` 가 하나 늘었다.** `dist/` 가 바뀐다. 설계 문서는 `docs/superpowers/specs/2026-08-26-pagination-stable-width-design.md` 다
- **`ns-sidebar` 단일 칼럼과 배지 삭제.** **breaking 이다(0.5.0).** 사이드바는 열리면 최상위 그룹이 전부 이어지고 **닫히면 폭이 0 이 되어 통째로 사라진다**(`--ns-sidebar-width-collapsed` 가 `4rem` → `0`). 열린 폭은 15rem 그대로다. `open` 이 **프로퍼티 전용**이 되어 `<ns-sidebar open>` 은 조용히 무시되고 경고가 뜬다(HTML 은 `default-open`). **`ns-nav-item` 의 `badge` 사각형이 없어졌다** — `leading` 슬롯이 폴백 없는 슬롯이 되어 비면 그 자리가 접히고, 항목 hover 가 배경뿐 아니라 글자색도 올린다. 신호 프로퍼티 둘(`--ns-label-display`·`--ns-group-list-display`)이 사라졌다. **닫힘은 폭 0 에서 멈추지 않는다** — 호스트가 상태와 무관하게 양방향을 자르고(`overflow: hidden`), 폭 전환이 끝나는 200ms 뒤에 안쪽 `nav` 가 `visibility: hidden` 으로 숨어 탭 순서와 접근성 트리에서 빠진다. `nav` 의 `min-width` 를 지워 `ns-sidebar { width: … }` override 가 되살아났다. **`dist/` 가 바뀐다.** 설계 문서는 `docs/superpowers/specs/2026-08-26-sidebar-rail-and-nav-subcategory-design.md` 이고 **§0 이 §1~§6 을 뒤집는다 — §0 을 먼저 읽는다.**
- **`ns-nav-group` 하위 카테고리.** `ns-nav-group` 을 `ns-nav-group` 안에 그냥 중첩하면 하위 카테고리가 된다 — 새 태그·이벤트·프로퍼티가 없다. 그룹이 `connectedCallback` 에서 `this.parentElement?.closest("ns-nav-group")` 로 자기 중첩을 스스로 판정하고, 들여쓰기는 **자기 shadow 안**에서 건다(부모 shadow 가 자식 shadow 를 볼 수 없어서). 2단까지 시각적으로 구분되고(들여쓰기·글자 굵기·자간) 3단 이상은 들여쓰기만 계속 누적된다. **그룹 헤딩의 글자 크기가 `--ns-font-size-sm` 로 올라가 항목 라벨과 같아진다** — 위계를 들여쓰기가 지므로 크기로 또 나누지 않는다는 판단이다. **`dist/` 가 바뀐다.** 설계 문서는 위와 같다

## B. 이 저장소에서 재현할 수 없다

### B-1. React `Dialog` 의 footer 버튼이 가운데로 오고 사이가 벌어지는가

`index.html` 에는 React 가 없어 shim 이 만드는 래퍼(`<div slot="footer" style="display: contents">`)를 여기서는 볼 수 없다. **`npm run check` 가 초록인 것은 이 항목에 대해 아무 증거도 아니다** — 타입만 맞으면 통과하고, `display: contents` 가 실제로 래퍼를 비켜서게 하는지는 렌더해야 안다.

- **볼 것:** `footer={<><Button variant="outline" size="sm">취소</Button><Button size="sm">확인</Button></>}` 로 대화상자를 열어 ① 두 버튼 묶음이 하단 **가운데**에 있다 ② 두 버튼 사이가 `--ns-space-2`(0.5rem)만큼 벌어져 있다 ③ 버튼 하나만 넘겼을 때(`docs/consumer-example.tsx` 가 그 모양이다)도 가운데다
- **잘못된 것:** 버튼 묶음이 오른쪽에 붙어 있다 · 두 버튼이 서로 맞닿아 한 덩어리로 보인다 · 버튼이 footer 폭 전체로 늘어난다(`display: contents` 가 먹지 않고 래퍼가 flex 항목으로 남은 것)
- **Tailwind 소비자에서 함께 본다:** preflight 는 `display` 를 건드리지 않으므로 영향이 없어야 한다. 그래도 위 셋을 그대로 다시 본다

### B-2. Next.js SSR 에서 `default-collapsed` 그룹이 첫 페인트부터 접혀 있는가

**볼 것:** 소비자 Next.js 프로젝트에서 `default-collapsed` 그룹이 있는 페이지를 새로고침하며, devtools 의 CPU 스로틀링(4배 이상)이나 paint flashing, 또는 화면을 슬로모션으로 녹화한 뒤 프레임 단위로 돌려 본다 — 위험 구간이 한 프레임짜리라 맨눈의 실시간 관찰로는 놓치기 쉽다.

**무엇이 잘못된 것인가:** 펼쳐진 채로 한 프레임 그려졌다가 접히는 것. **최종 상태는 어느 쪽이든 맞다** — `willUpdate` 씨앗이 늦게 도착한 값을 반영하므로 "펼쳐진 채로 남는" 결함은 없다. 남는 위험은 한 프레임뿐이다.

**이 위험이 낮다고 보는 근거.** 문제의 구간은 업그레이드와 하이드레이션 사이인데, `createComponent` 는 **모든** 반응형 프로퍼티를 `useLayoutEffect` 에서만 설정하므로 `label`·`heading` 도 같은 구간을 겪는다. 그 구간에서 페인트가 일어난다면 이번 변경 **전에도** 항목 글자가 비어 있다가 채워지는 것이 보였어야 하고, 소비자 프로젝트에서 그것이 관측된 적이 없다.

`ns-sidebar` 의 `data-ns-open` 과 `ns-icon` 의 문서 트리 짝이 이 종류를 방어하지만, **그 둘이 실제로 관측한 것은 업그레이드 *전* 구간이다**(예약이 그린 4rem 이 15rem 으로 벌어진 것, 아이콘 자식이 24 에서 20 으로 줄어든 것). `data-ns-open` 자체는 `ns-sidebar.styles.ts` 의 세 구간짜리 타임라인대로 업그레이드 전과 업그레이드 ↔ 하이드레이션 사이 **둘 다** 방어하도록 되어 있지만, 관측 기록이 있는 것은 그중 업그레이드 전 구간뿐이다. 업그레이드 ↔ 하이드레이션 구간은 그 주석들이 **예측**으로 방어한 것이고 관측 기록이 없다. 그룹의 접힘은 업그레이드 전에 아무것도 그리지 않으므로(항목의 내용이 자기 shadow 안에 있다) 오직 이 미관측 구간에만 걸린다.

**여기서 깜빡임이 실제로 보이면 처방이 정해져 있다** — React shim(`src/react/tags/NavGroup.tsx`)이 `data-ns-collapsed` 를 서버 마크업에 실어 보내고 `connectedCallback` 이 그것을 씨앗으로 읽는 것이다. 다만 그 shim 은 이름 규칙상 `NsNavGroup` → `NavGroup` 개명(breaking)을 데려오므로, **관측 없이 미리 지불하지 않는다.** 별도 릴리스로 낸다.

- **릴리스 때 할 일:** 없다. 낮은 위험으로 판단해 이번 릴리스를 막지 않는다. 깜빡임이 보이면 위 shim 을 별도 릴리스로 낸다.

### B-3. Next.js SSR 에서 `default-open` 사이드바가 첫 페인트부터 15rem 인가

**이 사이클에서 가장 중요한 B 항목이다.** `ns-sidebar` 의 `willUpdate` 씨앗과 `Sidebar` shim 의 `default-open`·`data-ns-open` 두 통로가 막으려는 것이 정확히 이 구간이고, `index.html` 은 순수 HTML 이라 **이 경로를 재현하지 못한다.** `npm run check` 가 초록인 것은 이 항목에 대해 아무 증거도 아니다 — 타입은 맞고, 문제는 upgrade·hydration·`useLayoutEffect` 의 시점이다.

**닫힌 폭이 `0` 이 되면서 증상이 더 눈에 띈다.** 0.4.0 에서는 4rem 이 잠깐 그려졌다 넓어지는 것이었지만, 지금은 **사이드바가 아예 없다가 나타난다** — 본문이 좌측으로 붙었다가 15rem 밀린다.

- **볼 것:** 소비자 Next.js 프로젝트에서 ① `<Sidebar defaultOpen>`(비제어)와 ② `<Sidebar open={true}>` + 헤더의 `onNsToggle`(제어) 두 가지로 페이지를 새로고침한다. devtools 의 CPU 스로틀링(4배 이상)이나 paint flashing 을 켜거나, 화면을 녹화해 프레임 단위로 돌려 본다 — 위험 구간이 한두 프레임이다. 첫 프레임부터 **15rem** 이어야 한다
- **잘못된 것:** 사이드바가 없는 채로 그려졌다가 200ms 동안 15rem 으로 벌어진다 · 첫 페인트는 15rem 인데 번들 실행 직후 한 번 사라졌다 돌아온다 · 갱신마다 사이드바가 열리고 닫힌다(씨앗이 `undefined` 를 통과시켜 `toggleAttribute` 의 두 번째 인자가 토글로 동작하는 것이다 — `willUpdate` 의 `=== true` 좁히기가 그것을 막는다)
- **함께 볼 것:** 콘솔에 `[ns-sidebar]` 로 시작하는 경고가 **한 번도 뜨지 않아야 한다.** 반대로 마크업에 `<ns-sidebar open>` 을 일부러 써 보고 프로퍼티 전용 경고가 **뜨는지**도 확인한다 — 그 경고가 죽어 있으면 소비자의 실수가 조용해진다
- **릴리스 때 할 일:** 튐이 보이면 이번 릴리스를 막는다. 통로 둘 중 어느 쪽이 끊긴 것인지는 서버 HTML 을 그대로 보면 갈린다 — `default-open` 이 마크업에 실려 있는지, 제어 모드에서 `data-ns-open` 이 함께 실려 있는지

## A. 이 저장소의 `index.html` 에서 확인한다

### A-1. 이관 절을 걷어낸 자리가 매끄럽게 이어지는가

지운 곳이 다섯이라 **끊긴 자리나 죽은 링크가 남기 쉽다.** 지운 것 자체는 되돌아볼 필요가 없고, 남은 문서가 그 자리에서 자연스럽게 이어지는지만 본다.

- **볼 것:** ① 설치 절의 업그레이드 안내가 **한 문단**으로 줄었고 그 안에 링크가 없다 ② 사이드바 「시작하기」 그룹에 **설치 · 환경별 연동** 둘만 있다 ③ 「Tailwind 를 쓰면 레이어 순서를 선언해야 한다」 절 다음이 곧바로 「환경별 연동」이다 ④ 「디자인 토큰」 절의 액센트 설명 두 벌(선·링 / 채움면)과 코드 블록, 그 아래 스와치 격자가 그대로다 ⑤ `nsToast` 절이 「위치」 표 → 「인자」 → 「JS」 → 「주의」로 끊김 없이 이어진다
- **잘못된 것:** 사이드바 항목을 눌렀는데 페이지 맨 위로 튄다(지운 앵커를 가리키는 링크가 남은 것) · 제목만 있고 본문이 없는 절이 보인다 · 절 사이 여백이 다른 곳과 눈에 띄게 다르다
- **릴리스 때 할 일:** 없다. 이 항목은 문서만 고쳤다

### A-2. 토스트의 닫기 버튼이 글자와 세로 중심이 같은가

`nsToast` 절의 버튼으로 네 tone 을 모두 띄운다. 기준은 **이미 맞아 있던 좌측 점**이다 — 점과 닫기 아이콘과 첫 줄 글자, 셋의 세로 중심이 한 줄에 있어야 한다.

- **볼 것:** ① 한 줄짜리 토스트에서 `×` 아이콘의 중심이 글자의 중심과 같은 높이다 ② `neutral`(점이 없는 것)에서도 같다 ③ **긴 메시지로 두 줄 이상이 될 때** 점과 `×` 가 **첫 줄**의 중심에 있다(가운데 줄이 아니다 — 여러 줄에서 블록 전체의 가운데로 오면 그것이 잘못된 것이다) ④ 토스트 상자의 높이가 예전보다 늘거나 줄지 않았다 ⑤ 닫기 버튼에 마우스를 올렸을 때 생기는 사각 배경이 토스트 위아래 경계선을 넘지 않는다
- **잘못된 것:** `×` 가 글자보다 아래에 있다(고치기 전 상태다) · `×` 가 상자 위 테두리에 닿거나 밖으로 나간다 · hover 배경이 상자 밖으로 삐져나온다 · 네 자리(`top-center`·`bottom-center`·`top-right`·`bottom-right`) 중 어디선가만 다르다
- **릴리스 때 할 일:** 없다 — `scripts/release.mjs` 가 태그 커밋에서 `dist/` 를 새로 빌드한다. 다만 이 항목은 **소비자에게 나가는 코드**라, 문서만 고친 A-1 과 달리 태그가 실제 동작을 바꾼다

### A-3. 대화상자 footer 버튼이 하단 가운데에 있고 사이가 벌어지는가

`ns-dialog` 데모(비제어)와 `nsAlert` · `nsConfirm` · `nsConfirm (danger)` 버튼 넷을 모두 눌러 본다. **`nsConfirm` 두 개가 이 변경의 핵심 증거다** — 고치기 전에는 취소와 확인이 서로 맞붙어 있었다.

- **볼 것:** ① 데모의 취소 · 승인이 하단 **가운데**에 있고 사이가 `--ns-space-2` 만큼 벌어져 있다 ② `nsAlert` 의 확인 버튼 하나가 가운데다 ③ `nsConfirm` 의 취소 · 확인이 가운데이고 **서로 붙어 있지 않다** ④ `nsConfirm (danger)` 도 같고, 열리자마자 **취소**에 포커스 링이 있다 ⑤ 취소를 눌러 닫으면 포커스가 열었던 버튼으로 돌아온다 ⑥ footer 아래·좌우 여백이 예전과 같다
- **잘못된 것:** 버튼이 오른쪽에 붙어 있다 · 두 버튼이 맞닿아 있다 · 취소와 확인의 **순서가 뒤바뀌었다**(문서 순서로 배정되므로 취소가 왼쪽이어야 한다) · danger 에서 초기 포커스가 확인에 간다(콘솔에 `[ns-confirm]` 경고가 함께 뜬다) · footer 영역이 내용 없이 남아 있다
- **릴리스 때 할 일:** 없다 — `scripts/release.mjs` 가 태그 커밋에서 `dist/` 를 새로 빌드한다. 다만 이 항목은 **소비자에게 나가는 코드**라, 문서만 고친 A-1 과 달리 태그가 실제 동작을 바꾼다

### A-4. Safari 에서 대화상자 본문에 스크롤 막대가 없는가

**이 항목만 Chrome 이 아니라 Safari 로 본다.** 고치기 전 결함이 WebKit 에서만 나타났고, Chrome 에서는 처음부터 정상으로 보였다 — 여기서 Chrome 만 보면 아무것도 검증되지 않는다.

- **볼 것:** Safari 로 `index.html` 을 열고 ① `ns-dialog` 데모 ② `nsAlert` ③ `nsConfirm` 을 각각 띄워, 한 줄짜리 본문 오른쪽에 **스크롤 막대가 없다** ④ 본문 글자가 잘리지 않고 위아래 여백이 Chrome 과 같아 보인다
- **긴 본문도 함께 본다:** 본문이 화면을 넘길 만큼 긴 대화상자에서는 **본문만** 스크롤되고 제목 줄과 버튼 줄은 제자리에 고정돼야 한다. 그 스크롤은 정상이다 — 없어져야 하는 것은 짧은 본문의 스크롤이다
- **잘못된 것:** 짧은 문장인데 스크롤 막대가 있다(고치기 전 상태다) · 본문 영역이 패딩만 남고 글자가 안 보인다 · 긴 본문에서 대화상자 전체가 화면 밖으로 넘어간다
- **릴리스 때 할 일:** 없다 — `scripts/release.mjs` 가 태그 커밋에서 `dist/` 를 새로 빌드한다. 다만 이 항목은 **소비자에게 나가는 코드**라, 문서만 고친 A-1 과 달리 태그가 실제 동작을 바꾼다

### A-5. `collapsible` 없는 그룹이 이전과 같은가

- **볼 것:** `ns-nav-group` 절(`#ns-nav-group`) 데모의 「프로젝트」 그룹(`collapsible` 을 쓰지 않았다) 헤딩에 마우스를 올린다.
- **잘못된 것:** hover 색 변화·커서 변화·caret 이 **보이면** 결함이다 — `collapsible` 을 쓰지 않으면 렌더 결과가 이전과 같아야 한다.
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. `ns-nav-group` 의 조건부 렌더 분기가 깨진 것이다.

### A-6. caret 이 보이는지, 그리고 접힘/펼침에 따라 방향이 맞는지

- **볼 것:** `ns-nav-group` 절(`#ns-nav-group`) 데모의 「관리」 그룹 헤딩 오른쪽의 caret. 펼친 상태와, 헤딩을 눌러 접은 상태를 각각 본다.
- **잘못된 것:** caret 이 아예 안 보이거나, 펼친 상태에서 아래(▾)가 아니거나 접힌 상태에서 오른쪽(▸)이 아니면 결함이다. spec §6 이 caret 회전을 유일한 상태 표시로 두었으므로 이것이 안 보이면 접힘에 어포던스가 하나도 없다.
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다.

### A-7. 헤딩 버튼의 포커스 링이 잘리지 않는가

`outline-offset` 이 음수(`-2px`)인 이유가 이것이다 — 사이드바 안의 `<nav>` 가 `overflow-x: hidden` 이라 링을 버튼 바깥에 그리면 잘린다.

- **볼 것:** `ns-nav-group` 절(`#ns-nav-group`)의 데모에서 Tab 키로 「사용자 관리」·「보관」 헤딩 버튼까지 이동한다. **문서 셸의 좌측 네비게이션에서도 같은 것을 본다** — 그쪽 최상위 그룹이 이제 전부 `collapsible` 이고, 사이드바 폭 전체를 채우는 버튼이라 잘림이 나타난다면 그 자리다.
- **잘못된 것:** 포커스 링이 그룹 폭 밖으로 잘리거나 인접 요소에 가려지면 결함이다.
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다.

### A-8. `button.heading` 이 `div.heading` 과 같은 자리에 놓이는가 — Safari 는 따로 본다

`<button>` 의 UA 기본값은 엔진마다 다르고 Safari 는 `-webkit-appearance` 때문에 폰트·패딩·정렬이 Chrome 과 어긋나는 이력이 있다. shadow 리셋이 `width`·`border`·`background`·`font-family`·`text-align` 만 되돌리므로, 남은 UA 값이 어긋나면 **접히는 그룹의 제목만 한 칸 밀린다.**

- **볼 것:** `ns-nav-group` 절(`#ns-nav-group`)의 데모에서 `collapsible` 있는 그룹(「관리」·「보관」)과 없는 그룹(「프로젝트」)의 헤딩을 나란히 두고 좌측 정렬과 줄 높이를 비교한다. **Chrome 과 Safari 양쪽에서** 본다 — 한 엔진만 본 확인은 증거가 아니다.
- **잘못된 것:** `collapsible` 헤딩만 왼쪽 시작 위치가 다르거나 줄 높이가 달라 텍스트 기준선이 어긋나면 결함이다.
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다.

### A-9. 페이지를 끝까지 넘기는 동안 "다음" 버튼이 제자리에 있는가

**페이지네이션 변경의 핵심 증거다.** `ns-pagination` 절의 첫 데모(`total="240" per-page="20"`, 12페이지)를 쓴다. "다음" 을 1페이지부터 12페이지까지 누르고 "이전" 으로 되돌아온다. **버튼을 누른 뒤 마우스를 움직이지 않는 것이 요령이다** — 커서 아래에서 버튼이 빠져나가면 그것이 곧 결함이다.

- **볼 것:** ① "다음" 버튼의 왼쪽 모서리가 1 → 12 → 1 내내 같은 x 좌표에 있다 ② "이전" 버튼도 같다 ③ **4→5 와 9→10 경계**에서도 그렇다(고치기 전 진폭이 가장 컸던 자리다) ④ 번호 칸과 `…` 칸의 폭이 서로 같다 ⑤ 어느 페이지에서도 번호 칸이 정확히 7개다
- **잘못된 것:** 특정 페이지에서만 버튼이 튄다 · `…` 칸이 번호 칸보다 눈에 띄게 좁다 · 현재 페이지가 `12` 일 때만 전체 폭이 살짝 넓어진다(테두리 2px 이 안 맞은 것이다) · 1페이지와 12페이지에서 번호 개수가 다르다
- **릴리스 때 할 일:** `README.md` 의 릴리스 표에 한 행을 더한다 — `ns-pagination` 이 `<span class="ns-pagination-pages">` 래퍼를 새로 렌더하므로, 번호 버튼을 `ns-pagination nav > button` 으로 겨냥하던 소비자 CSS 는 깨진다. 이 항목만 위 다섯과 달리 `dist/` 밖에도 흔적을 남긴다

### A-10. `page-window` 가 실제로 듣고, 잘못된 값이 경고와 함께 7로 떨어지는가

`ns-pagination` 절의 「슬롯 수」 데모 셋을 쓴다. 그 다음 **콘솔을 연 채로** 개발자 도구에서 값을 잘못 넣어 본다.

```js
document.querySelector("#pagination-window-demo ns-pagination").setAttribute("page-window", "6")
```

- **볼 것:** ① 세 컨트롤의 번호 칸이 각각 5개 · 7개 · 9개다 ② 셋 다 각자 끝까지 넘기는 동안 "다음" 이 제자리다 ③ `page-window="5"` 에서 가운데 배치가 `1 … 6 … 12` 모양이다(현재 페이지 좌우에 번호가 없다) ④ 위 `setAttribute` 뒤 콘솔에 `[ns-pagination] page-window=6 는 5 이상의 홀수여야 합니다. 7 로 그립니다.` 가 **한 번만** 뜨고 칸이 7개가 된다 ⑤ 같은 컨트롤에 `"3"`·`"abc"` 를 다시 넣어도 **경고가 더 뜨지 않는다**(인스턴스당 한 번이다)
- **잘못된 것:** 세 컨트롤의 칸 수가 같다(속성이 안 먹은 것) · 잘못된 값에서 아무것도 안 그려진다(렌더를 멈추면 안 된다) · 경고가 렌더마다 반복된다 · 경고가 아예 없다
- **릴리스 때 할 일:** 없다. 위와 같다

### A-11. 현재 페이지 테두리와 `…` 정렬이 살아 있는가

투명 테두리 규칙(`.ns-pagination-pages > .ns-button--ghost`)을 잘못 쓰면 **현재 페이지의 테두리가 사라진다.** 폭은 고정된 것처럼 보이므로 A-9 만으로는 안 잡힌다. 밝은 모드와 다크 모드 양쪽에서 본다.

- **볼 것:** ① 현재 페이지 버튼에 테두리가 **보인다**(`--outline` 변형이다) ② 나머지 번호 버튼에는 테두리가 **안 보인다** ③ `…` 이 칸 안에서 가로·세로 모두 가운데다 ④ 번호 버튼의 높이가 "이전"·"다음" 과 같다 ⑤ 다크 모드에서 투명 테두리가 미묘한 선으로 드러나지 않는다
- **잘못된 것:** 현재 페이지에 테두리가 없다(선택자를 `> .ns-button` 으로 넓힌 것이다) · 모든 번호에 테두리가 보인다 · `…` 이 칸 위쪽에 붙어 있다(부모의 `align-items: center` 가 빠진 것이다) · 번호 버튼만 2px 높다
- **릴리스 때 할 일:** 없다. 위와 같다

### A-12. 전부 표시 배치·100페이지 이상·키보드 포커스가 각각 규칙을 지키는가

A-9·A-10·A-11 가 다루지 않는 세 자리다. 셋은 서로 다른 실패 지점을 겨냥하므로 하나라도 건너뛰면 그 지점은 이번 사이클에서 아무도 보지 않은 채로 남는다.

- **볼 것:** ① 「경계」 데모의 첫 컨트롤(`total="60"`, 3페이지)에서 `…` 없이 페이지 셋이 전부 그려진다 ② 그 3페이지 사이를 넘기는 동안에도 "다음" 버튼이 움직이지 않는다(슬롯 수가 `min(pages, size)` 라 3인 경로다) ③ 「슬롯 수」 데모의 네 번째 컨트롤(`total="2200"`, 110페이지)에서 창 안의 두 자리 번호(`49`)와 세 자리 번호(`110`)의 글자 폭이 자릿수에 비례한다 — `1` 같은 좁은 숫자가 들어간 자리와 `0` 처럼 넓은 숫자가 들어간 자리라도 칸 폭이 서로 다르지 않다 ④ 그 컨트롤에서도 끝까지 넘기는 동안 "다음" 이 제자리다 ⑤ 「데모」 절의 12페이지 컨트롤에서 "다음" 에 Tab 으로 도달한 뒤 Enter 를 연타해 마지막 페이지까지 간다 ⑥ 그동안 포커스 링이 "다음" 버튼에 계속 남아 있다
- **잘못된 것:** 3페이지 컨트롤에 `…` 이 보이거나 칸이 7개로 채워져 있다(빈 칸으로 채우지 않는다는 §3 의 결정을 어긴 것이다) · 110페이지 컨트롤에서 페이지를 넘길 때 "다음" 이 흔들린다(`tabular-nums` 가 안 먹혀 자릿수가 같아도 폭이 달라진 것이다) · Enter 를 몇 번 누른 뒤 포커스가 `<body>` 나 페이지 맨 위로 떨어진다(`aria-disabled` 대신 `disabled` 가 쓰인 것이다 — 포커스된 요소가 `disabled` 되면 브라우저가 blur 시킨다)
- **릴리스 때 할 일:** 없다 — `scripts/release.mjs` 가 태그 커밋에서 `dist/` 를 새로 빌드한다. 다만 이 항목은 **소비자에게 나가는 코드**라 태그가 실제 동작을 바꾼다

### A-13. 일부 항목에만 `leading` 을 줬을 때 줄이 들쭉날쭉해 보이는가 — **이번 변경에서 가장 판정이 필요한 자리다**

**배지를 없애면서 강제 정렬을 포기했다.** 0.4.0 은 `leading` 이 비면 `badge` 가 그 자리를 채웠으므로 한 목록의 모든 항목이 같은 x 좌표에서 라벨을 시작했다. 지금 `leading` 은 폴백 없는 슬롯이라 **배정된 것이 없으면 상자도 `gap` 도 만들지 않고**, 그래서 아이콘이 있는 줄과 없는 줄의 라벨 시작 위치가 달라진다. 그 포기가 옳았는지는 **눈으로만 판정된다.**

- **볼 것:** `ns-nav-item` 절(`#ns-nav-item`)의 데모가 정확히 그 상태다 — 넷 중 마지막 하나에만 `leading` 아이콘이 있고 셋은 비어 있다. ① 아이콘 있는 줄의 라벨이 없는 줄보다 오른쪽에서 시작한다(이것이 의도한 결과다) ② 그 차이가 **아이콘 폭 + `--ns-space-2-5` 만큼**이고 그 이상 벌어지지 않는다 ③ 네 줄의 세로 간격·행 높이는 서로 같다 ④ hover 배경의 좌우 끝은 네 줄 모두 같은 자리다
- **무엇이 잘못된 것인가:** **"들쭉날쭉하다" 는 취향이 아니라 판정이다.** ① 라벨 시작 위치가 두 가지가 아니라 셋 이상이면 결함이다(빈 슬롯이 폭을 조금씩 남기고 있는 것이다 — 완전히 접히지 않았다) ② 아이콘 있는 줄만 행 높이가 다르면 결함이다 ③ hover 배경의 끝이 줄마다 다르면 결함이다. **이 셋이 전부 정상인데도 목록이 어수선해 보인다면 그것은 결함이 아니라 설계 판단**이고, 그때 답은 라이브러리가 빈 상자를 되살리는 것이 아니라 **소비자가 한 목록 안에서 전부 주거나 전부 비우는 것**이다(`README.md` 의 0.5.0 이주 절이 그렇게 권한다). 어수선함이 그 권고로 감당되지 않는다고 판단되면 이 릴리스를 막지 말고 별도로 다시 논의한다
- **릴리스 때 할 일:** 위 ①②③ 중 하나라도 걸리면 이번 릴리스를 막는다. 셋이 정상인데 보기가 나쁜 것은 막지 않는다

### A-14. `leading` 이 빈 항목의 글자가 왼쪽 끝까지 붙는가

**빈 슬롯이 상자를 만들지 않는다는 주장의 직접 증거다.** `<slot>` 의 UA 기본값이 `display: contents` 라 배정된 것이 없으면 flex 항목이 하나도 생기지 않고, 그래서 `.row` 의 `gap` 도 발동하지 않는다. **`gap` 이 남으면 라벨이 이유 없이 10px 밀린다.**

- **볼 것:** 문서 셸의 좌측 네비게이션(어느 항목에도 `leading` 이 없다)에서 ① 항목 라벨의 왼쪽 끝이 그룹 제목의 왼쪽 끝과 같은 x 좌표다 ② 그 값이 `ns-nav-group` 절 데모의 「프로젝트」 그룹에서도 같다 ③ 라벨과 행 배경 왼쪽 끝 사이가 행 패딩(`--ns-space-2` = 8px)뿐이다
- **무엇이 잘못된 것인가:** 라벨이 그룹 제목보다 오른쪽에서 시작한다 — 빈 슬롯이 `gap` 을 남긴 것이다. 브라우저 devtools 로 `.row` 의 flex 항목 수를 세면 갈린다(라벨과 `.trailing` 둘이어야 한다). **폭 0 짜리 상자 하나가 남아 있는 것은 화면에서 8~10px 로만 보이므로, 이 항목이 없으면 아무도 알아채지 못한다**
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다

### A-15. 항목 hover 의 글자색 상승이 그룹 제목 hover 와 겨루지 않는가

**같은 규약을 두 자리가 함께 쓰게 됐다.** `collapsible` 인 그룹 제목은 이미 hover 에서 글자색만 올렸고(`--ns-color-fg-subtle` → `--ns-color-fg-body`), 이번에 `ns-nav-item` 의 hover 가 배경뿐 아니라 글자색까지 올린다(`--ns-color-fg-body` → `--ns-color-fg`). 둘이 나란히 있는 목록에서 **어느 줄에 마우스가 있는지 헷갈리면** 규약이 실패한 것이다.

- **볼 것:** 문서 셸의 좌측 네비게이션에서(최상위 그룹이 전부 `collapsible` 이라 두 종류가 나란히 있다) ① 제목 줄에 올렸을 때 **배경은 변하지 않고 글자색만** 올라간다 ② 항목 줄에 올렸을 때 **배경과 글자색이 함께** 올라간다 ③ 그래서 지금 커서가 제목 위인지 항목 위인지 한눈에 갈린다 ④ hover 한 항목이 **활성 항목과도** 구분된다(활성은 더 진한 배경 `--ns-color-surface-hover` 다) ⑤ **라이트·다크 양쪽에서** 위 넷이 같다
- **무엇이 잘못된 것인가:** 제목 hover 에도 배경이 생긴다 · hover 한 항목과 활성 항목이 같아 보인다(현재 위치를 잃는다) · 한쪽 모드에서만 구분된다 · 글자색 상승이 아예 안 보인다(전환이 `--ns-transition-fast` 이므로 마우스를 멈춰 놓고 본다)
- **릴리스 때 할 일:** ①②④ 중 하나라도 걸리면 이번 릴리스를 막는다. ③⑤ 는 대비 조정으로 별도 처리할 수 있다

### A-16. 문서 셸의 최상위 그룹이 실제로 접히고, 접은 상태가 페이지를 쓰는 데 방해되지 않는가

**이 저장소가 자기 기능을 먹는 자리다.** 좌측 문서 네비게이션의 최상위 그룹 다섯(「시작하기」·「기초」·「클래스」·「컴포넌트」·「예시」)에 `collapsible` 을 붙였다. 기본은 전부 펼침이라 페이지를 열었을 때의 모양은 예전과 같아야 한다.

- **볼 것:** ① 페이지를 열면 다섯 그룹이 **전부 펼쳐진** 채다 ② 제목을 누르면 그 그룹만 접히고 나머지는 그대로다 ③ 접은 상태에서 다른 그룹의 항목을 눌러 이동해도 접힘이 유지된다 ④ 스크롤에 따라 `active` 가 옮겨 다니는 동작이 접힌 그룹에서도 예외를 내지 않는다(콘솔이 조용해야 한다 — 접힌 그룹의 항목은 `display: none` 이지만 `IntersectionObserver` 는 관찰 대상이 본문 쪽이라 계속 돈다) ⑤ 다섯을 전부 접으면 사이드바가 제목 다섯 줄로 줄어든다
- **무엇이 잘못된 것인가:** 페이지를 열자마자 접혀 있다(`default-collapsed` 가 잘못 붙은 것) · 하나를 접었는데 다른 그룹도 함께 접힌다 · 접힌 그룹의 항목으로 스크롤이 갔을 때 콘솔에 예외가 난다 · caret 이 안 보인다
- **릴리스 때 할 일:** 없다. `index.html` 만의 변경이라 `dist/` 에 흔적이 없다 — 다만 ④ 가 깨지면 배선 스크립트가 그 지점부터 죽으므로 **화면이 멀쩡해 보여도 아래 절이 전부 고장난다.** 콘솔을 열고 본다

### A-17. 하위 제목이 상위 제목과 구분되어 읽히는지 (다크·라이트)

**하위 카테고리의 판정은 JS 지만 시각적 차이는 CSS 하나(`[role="group"].nested > .heading`)뿐이다.** 게다가 **이번에 그룹 헤딩의 글자 크기가 `--ns-font-size-sm` 로 올라가 항목 라벨과 같아졌으므로**, 남은 구분 수단은 **들여쓰기 · 굵기 · 자간** 셋이다. 크기로 나누던 것을 놓았을 때 그 셋으로 충분한지가 이 항목이다.

`ns-nav-group` 절의 중첩 데모(`#nav-group-nested-demo`)에서 최상위 「관리」 헤딩과 하위 「사용자」·「결제」 헤딩을 나란히 본다.

**④ 는 데모 그대로는 판정되지 않는다.** 데모의 하위 그룹 둘이 **모두 `collapsible`** 이라 caret·포인터 커서·hover 색 상승이 붙어 있고, 그 셋이 있으면 ④ 는 저절로 통과한다. 위험한 배치는 **`collapsible` 이 없는 하위 헤딩**이다 — 크기가 통일된 뒤 그 줄은 자기 아래 항목 라벨과 크기·줄 높이·굵기(둘 다 medium)·자간(둘 다 normal)·왼쪽 끝(둘 다 28px)이 **전부 같고**, 남는 정적 차이가 색 하나(`--ns-color-fg-subtle` 70.5% 대 `--ns-color-fg-body` 37%)뿐이다. 그 배치는 이 파일 어디에도 데모가 없으므로 콘솔로 만든다.

```js
document.querySelector("#nav-group-nested-demo ns-nav-group[heading='사용자']").removeAttribute("collapsible")
```

- **볼 것:** ① 하위 헤딩이 최상위보다 왼쪽으로 더 들여쓰기 되어 있다 ② 하위 헤딩의 글자 굵기가 최상위보다 얇다(semibold 대 medium) ③ 최상위 헤딩에는 자간이 있고 하위 헤딩에는 없다 ④ **제목 줄과 항목 줄이 같은 크기인데도 어느 쪽이 제목인지 갈린다**(제목은 색이 `--ns-color-fg-subtle` 로 더 옅고 hover 배경이 없다) ⑤ 라이트·다크 양쪽에서 위 넷이 같다 ⑥ **위 스니펫으로 caret 을 없앤 「사용자」 헤딩에서도 ④ 가 성립한다** — caret 도 커서 변화도 hover 도 없는 상태에서, 색만으로 그 줄이 "누를 수 없는 제목" 으로 읽히는지 본다. 마우스를 올리지 않은 정지 화면에서 판정한다(hover 를 쓰면 판정할 것을 없애는 것이다)
- **무엇이 잘못된 것인가:** 들여쓰기가 없어 최상위와 같은 자리에서 시작한다 · 굵기가 최상위와 같다 · **제목이 항목처럼 보여 누를 수 있는 줄로 오인된다**(크기를 맞춘 대가가 여기서 나온다면 그것이 이 변경의 결함이다) · 한쪽 모드에서만 구분된다 · **⑥ 에서 색 하나로는 갈리지 않는다** — 이때 답은 크기를 되돌리는 것이 아니라 굵기나 자간 중 하나를 하위 헤딩에 돌려주는 것이고, 사용자가 "크기만" 을 요청했으므로 **묻고 결정한다**
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. 콘솔로 만든 상태는 새로고침하면 사라진다.

### A-18. 하위 항목의 hover 배경 오른쪽 끝이 상위 항목과 같은 자리인지

**하위 그룹은 `.list` 의 대칭 패딩을 버리고 왼쪽 들여쓰기만 갖는다** — 오른쪽 끝을 상위와 맞추기 위해서다. 중첩 데모는 최상위 그룹의 직속 항목(「로그」)과 하위 그룹 안 항목(「목록」·「권한」·「영수증」)을 한 그룹 안에 함께 갖고 있어 바로 비교할 수 있다.

- **볼 것:** 「로그」 행과 「목록」 행에 각각 마우스를 올려 hover 배경의 **오른쪽 끝 x 좌표**를 비교한다. 같은 자리여야 한다.
- **잘못된 것:** 하위 항목의 hover 배경 오른쪽 끝이 들여쓰기만큼 안쪽으로 짧다(계단이 보인다) · 반대로 사이드바 오른쪽 경계를 넘어간다
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다.

### A-19. 하위 그룹 caret 의 회전과 상위 그룹 caret 이 겨루지 않는지

**하위 그룹의 `ns-group-toggle` 은 `composed` 라 상위 그룹에도 도착한다.** 상위 그룹이 자기 caret 회전을 그 이벤트만으로 판단한다면 하위 그룹을 열고 닫을 때 상위 caret 도 함께 도는 결함이 생길 수 있다. 중첩 데모의 최상위 「관리」에는 `collapsible` 이 없어 caret 이 없으므로, 콘솔에서 잠시 붙여 셋을 나란히 본다. (좌측 문서 네비게이션에는 최상위 caret 이 이미 있지만 그쪽에는 하위 카테고리가 없어 이 항목을 판정하지 못한다.)

```js
document.querySelector("#nav-group-nested-demo ns-nav-group[heading='관리']").setAttribute("collapsible", "")
```

- **볼 것:** ① 최상위 「관리」에도 caret 이 생긴다 ② 하위 「사용자」·「결제」의 caret 을 각각 열고 닫아도 「관리」 caret 의 방향은 그대로다 ③ 반대로 「관리」를 접었다 펼쳐도 하위 두 caret 의 방향은 자기 접힘 상태를 유지한다(접힌 동안 화면에서 사라졌다 다시 나타날 뿐, 방향이 초기화되거나 뒤집히지 않는다)
- **잘못된 것:** 하위 caret 을 돌렸는데 상위 caret 도 같이 돈다 · 상위를 접었다 펼쳤더니 하위 caret 방향이 바뀌어 있다
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. 확인이 끝나면 새로고침해 되돌린다.

### A-20. 3단을 넣었을 때 무너지지 않는지

**제목 모양은 2단에서 멈추고 들여쓰기만 계속 누적된다.** 중첩 데모에 3단이 없으므로 콘솔로 하나 만든다.

```js
const inner = document.createElement("ns-nav-group");
inner.setAttribute("heading", "감사 로그");
const item = document.createElement("ns-nav-item");
item.setAttribute("href", "/audit");
item.setAttribute("label", "감사 로그");
inner.appendChild(item);
document.querySelector("#nav-group-nested-demo ns-nav-group[heading='사용자']").appendChild(inner);
```

- **볼 것:** ① 3단(「감사 로그」) 제목의 굵기·자간이 2단(「사용자」·「결제」)과 **같다**(제목은 2단에서 멈춘다) ② 3단의 들여쓰기가 2단보다 한 단 더 깊다(누적된다) ③ 사이드바 폭에서 가로 스크롤이나 글자 겹침이 없다 ④ 3단 항목의 hover 배경 오른쪽 끝도 A-18 와 같은 자리다
- **잘못된 것:** 3단 제목이 최상위 굵기로 보인다(누적 대신 리셋된 것) · 3단 들여쓰기가 2단과 같다(누적이 아예 안 된 것) · 가로 스크롤이 생긴다
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. 콘솔로 만든 상태는 새로고침하면 사라진다.

### A-21. 중첩 없는 기존 그룹이 0.4.0 과 같은지

**하위 카테고리 스타일은 `.nested` 클래스가 붙었을 때만 걸린다.** 중첩하지 않은 그룹은 이번 사이클 이전과 노드 구조가 같아야 한다. **다만 픽셀 단위로 같지는 않다** — 헤딩 글자 크기가 `--ns-font-size-xs` 에서 `--ns-font-size-sm` 로 올라갔고, `ns-nav-item` 의 배지 사각형이 없어졌다. 그 둘은 의도한 변화이고, **그 밖의 차이가 있으면 결함이다.**

- **볼 것:** `ns-nav-group` 절의 첫 데모(중첩되지 않은 「프로젝트」 그룹)와 `ns-sidebar` 절의 데모를 본다. ① 헤딩에 **들여쓰기가 없다** ② 헤딩 굵기·자간이 이전과 같다(진하고 자간이 있다 — 바뀐 것은 크기뿐이다) ③ 항목 행의 좌우 여백이 이전과 같다 ④ 항목 행의 높이가 이전과 같다(배지가 없어졌다고 줄어들면 안 된다 — 높이를 정하는 것은 라벨의 `line-height` 와 행 패딩이다)
- **무엇이 잘못된 것인가:** 중첩되지 않았는데도 들여쓰기나 얇은 굵기가 보인다(`.nested` 클래스가 잘못 붙은 것) · 항목의 오른쪽 끝이 예전과 달라졌다 · 행 높이가 줄었다
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다.

### A-22. 문서 셸의 사이드바가 첫 페인트부터 15rem 인가

**이 브랜치의 메커니즘이 막으려는 튐이 이 저장소 자신의 셸에 있었다.** 문서 셸은 제어 모드인데(파일 끝의 스크립트가 `docsNav.open` 을 세운다) `open` 이 프로퍼티 전용이 되면서 마크업에 아무 표시가 남지 않았고, 그래서 `dist/bundle.umd.js` 를 내려받는 동안 예약값으로 그려지다 벌어졌다. React shim 이 제어 모드에서 하는 것과 같은 짝(`default-open` + `data-ns-open`)을 마크업에 되돌려 고쳤다.

**닫힌 폭이 `0` 이라 실패 모습이 0.4.0 과 다르다.** 좁은 레일이 먼저 그려지는 것이 아니라 **사이드바가 아예 없이 본문만 그려졌다가** 15rem 이 밀고 들어온다.

- **볼 것:** `index.html` 을 캐시를 비우고 새로고침한다. devtools 의 네트워크 스로틀링을 `Slow 3G` 로 두면 번들을 내려받는 동안이 길어져 관측하기 쉽다. ① 좌측 사이드바가 **첫 페인트부터 15rem** 이다 ② 번들이 실행되는 순간 폭이 변하지 않는다 ③ 200ms 트랜지션을 타고 벌어지는 장면이 없다 ④ 로드가 끝난 뒤 헤더 토글로 접고 펴는 것이 여전히 동작하고, 접으면 **사이드바가 완전히 사라진다**(좁은 띠가 남지 않는다)
- **무엇이 잘못된 것인가:** 사이드바 없이 먼저 그려졌다가 밀고 들어온다 · 첫 페인트는 15rem 인데 번들 실행 직후 한 번 사라졌다 돌아온다(두 속성 중 하나만 있는 증상이다 — `data-ns-open` 만 있으면 첫 `updated()` 가 그것을 지우고, `default-open` 만 있으면 upgrade 전 구간이 비어 있다) · 접었는데 좁은 띠가 남는다(`--ns-sidebar-width-collapsed` 가 `0` 이 아닌 것)
- **④ 는 폭만 본다.** 폭이 0 이 되는 것만으로 ④ 는 통과하므로, 이 항목은 닫힘의 나머지 메커니즘(양방향 클립·`visibility` 로 탭 순서에서 빠지는 것·`min-width` 삭제)에 대해 **아무 증거도 아니다.** 그 셋은 A-25·A-26·A-27 이 본다
- **Safari 에서도 같은 것을 본다.** `:not(:defined)` 예약이 떨어지는 시점과 폭 트랜지션이 엔진마다 다르므로, 한 엔진만 본 것은 이 항목에 대해 증거가 아니다
- **릴리스 때 할 일:** 없다. `index.html` 만의 변경이라 `dist/` 에 흔적이 없다

### A-23. 사이드바 밖에 쌓은 최상위 그룹의 간격이 좁아진 것을 받아들일 수 있는가

**소비자에게 보이는 breaking 인데 이주 문서에만 있고 아무도 눈으로 보지 않았다.** 첫 형제가 아닌 그룹 wrapper 에 `padding-top: var(--ns-space-6)`(24px)을 얹던 규칙을 지웠으므로(레일 시절 그 `:first-child` 가 배정되지 않은 형제까지 세어 여백이 마크업 순서에 따라 달라졌다), 그룹을 평범한 컨테이너에 세로로 쌓으면 사이가 24px 좁아진다. 남는 것은 헤딩 자신의 16px 뿐이다.

- **볼 것:** `ns-nav-group` 절의 첫 데모(`<template class="ex">` 로 만드는 것 — 최상위 둘을 사이드바 없이 쌓은 모양이다)에서 ① 「프로젝트」의 마지막 항목과 「관리」 제목 사이가 **붙어 보이지 않는다** ② 두 그룹의 경계가 제목의 굵기·색만으로도 읽힌다 ③ 사이드바 안의 데모(`#sidebar-demo`)에서도 두 최상위 그룹 사이가 같은 간격으로 보인다 — 사이드바가 그룹을 전부 그리므로 이제 이 축이 사이드바 안에도 적용된다
- **잘못된 것:** 두 그룹이 한 그룹처럼 이어져 보인다 · 「관리」 제목이 위 항목의 hover 배경에 닿을 만큼 가깝다. **이 릴리스를 막지는 않는다** — 의도한 변경이고 `README.md` 의 0.5.0 이주 절이 되돌리는 CSS 한 줄을 안내한다. 보기 어려울 정도면 그 규칙을 다른 형태로 라이브러리에 다시 넣을지 별도로 판단한다
- **릴리스 때 할 일:** 없다. 이주 문서의 문구가 화면과 맞는지만 확인한다

### A-24. Safari 에서 하위 카테고리·배지 삭제 항목 전부

**한 엔진만 본 확인은 증거가 아니다.** 하위 카테고리는 새 CSS 선택자(`[role="group"].nested`)와 특정도 계산에 기대고, **빈 `<slot>` 이 폭을 남기지 않는 것은 슬롯의 UA 기본값(`display: contents`)에 기댄다** — 둘 다 엔진의 구현 차이가 드러날 수 있는 자리다.

- **볼 것:** Safari 로 `index.html` 을 열어 **A-13 ~ A-15 · A-17 ~ A-21 · A-25 ~ A-28** 를 그대로 다시 본다. 특히 A-14(빈 `leading` 이 폭을 남기지 않는가)는 Chrome 에서 정상이어도 WebKit 에서 8~10px 이 남을 수 있으므로 **건너뛰지 않는다.** A-25 ~ A-27 도 엔진 차이가 나는 자리다 — `visibility` 전이의 지연이 언제 도착하는지, 폭이 애니메이션하는 동안 클립이 어느 시점의 폭으로 걸리는지가 구현에 달렸다.
- **무엇이 잘못된 것인가:** 각 항목의 "무엇이 잘못된 것인가" 와 같다. **두 엔진 사이에 차이가 있는 것 자체가 결함이다.**
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다.

### A-25. 여닫는 200ms 동안 `<nav>` 가 본문 위로 그려지지 않는가

**`overflow: hidden` 이 상태와 무관하게 `:host` 에 걸려 있는 이유가 이것이다.** 닫힘 규칙 안에만 두면 `data-ns-open` 이 붙는 순간 그 규칙이 매칭을 멈추고, 호스트 폭은 아직 0 에서 15rem 으로 가는 중인데 안의 `<nav>` 는 이미 자기 폭으로 배치돼 있어 **200ms 내내 `<main>` 위에 그려진다.** 개발 중에 실제로 그랬고 고쳤다. 폭만 보는 A-22 ④ 는 이것을 잡지 못한다.

- **볼 것:** 문서 셸의 헤더 토글로 사이드바를 닫았다 열어 본다. 200ms 는 맨눈으로 판정하기 짧으므로 devtools 의 CPU 스로틀링(4배 이상)이나 화면 녹화 후 프레임 재생으로 늘려서 본다. ① **여는 동안** 사이드바의 오른쪽 경계선이 본문 글자 위를 훑고 지나가지 않는다 ② 항목 글자와 본문 글자가 겹쳐 보이는 프레임이 하나도 없다 ③ **닫는 동안**에도 같다 ④ 전환이 끝난 뒤 경계선이 정확히 15rem 자리에 있다
- **무엇이 잘못된 것인가:** 여는 200ms 동안 사이드바 내용이 본문 위에 겹쳐 그려진다 — `overflow` 가 닫힘 규칙 안으로 돌아간 증상이다. 닫는 쪽만 정상이고 여는 쪽만 겹치는 **비대칭**이 이 결함의 지문이다(닫힐 때는 규칙이 계속 매칭되므로 클립이 살아 있다)
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. 소비자에게 나가는 코드다

### A-26. 닫은 뒤 Tab 이 사이드바 안으로 들어가지 않는가

**폭 0 과 `overflow: hidden` 은 자르기만 한다.** 그것만으로는 보이지 않는 링크가 탭 순서에 그대로 남아, Tab 을 누르면 화면에 없는 곳으로 포커스가 사라진다. 그래서 폭 전환이 끝나는 200ms 뒤에 `nav` 를 `visibility: hidden` 으로 숨긴다. **닫힌 사이드바의 링크에 Tab 이 닿지 않는 것은 소비자가 기대해도 되는 보장이므로, 아무도 눈으로 보지 않은 채 나가면 안 된다.**

- **볼 것:** 문서 셸에서 헤더 토글로 사이드바를 닫고 **1초쯤 기다린 뒤**(지연이 끝나야 한다) 토글 버튼에 포커스를 두고 Tab 을 눌러 나간다. ① 포커스가 본문의 첫 링크로 간다 — 사이드바 항목을 하나도 거치지 않는다 ② 그 사이 화면이 갑자기 스크롤되거나 본문이 튀지 않는다(잘린 링크에 포커스가 내려앉으면 브라우저가 그것을 화면에 넣으려고 스크롤한다 — 그 스크롤이 곧 증상이다) ③ 다시 열면 Tab 이 사이드바 항목으로 정상적으로 들어간다 ④ 빠르게 닫고 열기를 여러 번 반복한 뒤 열린 상태에서 사이드바 내용이 **보인다**
- **이것은 정상이므로 신고하지 않는다.** ⓐ 닫자마자 200ms 안에 누른 Tab 은 아직 잘린 링크에 내려앉을 수 있다. ⓑ 닫을 때 포커스가 사이드바 안에 있었으면 숨김이 도착하는 200ms 시점에 브라우저가 그것을 blur 시켜 포커스가 `<body>` 로 떨어지고, 다음 Tab 이 문서 처음부터 다시 시작한다. **둘 다 "애니메이션을 보인 뒤에 숨긴다" 에 내재하는 절충이다** — 애니메이션 전에 숨기면 사이드바가 접히는 장면 없이 사라진다. 헤더 토글로 포커스를 옮겨 주는 것은 `ns-sidebar` 가 자기를 여는 버튼을 모르므로 할 수 없다
- **무엇이 잘못된 것인가:** ① 1초를 기다린 뒤에도 Tab 이 사이드바 항목에 들어간다(`visibility` 규칙이 걸리지 않은 것 — 회귀다) · ③ 열었는데도 항목에 Tab 이 들어가지 않는다(지연이 여는 쪽에도 걸린 것) · ④ 반복 토글 뒤 열린 사이드바가 비어 보인다(전이가 `hidden` 에 갇힌 것)
- **낭독기를 쓸 수 있으면 함께 본다.** 닫힌 상태에서 사이드바 링크가 읽히지 않아야 한다. 랜드마크가 그 상태에서 없어지는 것은 의도한 절충이고 `docs/gotchas.md` 에 근거가 있다
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. 소비자에게 나가는 코드다

### A-27. `ns-sidebar { width: … }` override 가 다시 동작하는가

**`nav` 의 `min-width: var(--ns-sidebar-width)` 를 지웠다.** 닫힐 때 내용이 찌그러지지 않게 하려던 것이었으나, 그것이 붙어 있으면 문서에 적은 폭 override 가 깨진다 — 토큰보다 좁은 값을 주면 `nav` 가 호스트 밖으로 삐져나온다. 콘솔로 만든다.

```js
document.getElementById("docs-nav").style.width = "12rem"
```

- **볼 것:** ① 사이드바의 오른쪽 경계선이 **12rem 자리**에 있다 ② 항목 라벨이 필요한 만큼 말줄임표로 줄어들고 잘려 나가지 않는다 ③ 본문이 12rem 부터 시작한다 ④ 그 상태에서 헤더 토글로 닫고 열어도 열린 폭이 12rem 이다(15rem 으로 돌아가지 않는다) ⑤ devtools 로 `ns-sidebar` 의 shadow 안 `nav` 의 계산된 폭을 읽어 **192px** 인지 확인한다
- **무엇이 잘못된 것인가:** ⑤ 가 240px 이다 — `min-width` 가 살아 있는 것이다. **이 결함은 화면에서 보이지 않을 수 있으므로 ⑤ 를 건너뛰지 않는다** — 호스트의 `overflow: hidden` 이 삐져나온 3rem 을 잘라내므로, 잘린 경계선이 없어 보이면서도 `nav` 는 실제로 넓은 상태일 수 있다. 함께 볼 것: 경계선이 아예 보이지 않는다(12rem 밖으로 밀려 잘린 것)
- **릴리스 때 할 일:** 결함이면 이번 릴리스를 막는다. `README.md` 가 이 override 를 문서화하고 있다. 콘솔로 만든 상태는 새로고침하면 사라진다

### A-28. 헤딩 줄 상자가 커진 뒤에도 제목이 자기 아래 목록에 묶여 보이는가

**`.heading` 의 비대칭 세로 패딩은 줄 상자가 16px 이던 시절에 맞춘 값이다.** `padding: 1rem 1rem 0.5rem`(위 16 · 아래 8)이고, 글자 크기가 `--ns-font-size-sm` 로 올라가 줄 상자가 20px 이 됐다 — 블록 높이가 40px → 44px 로 커졌고 위:아래 2:1 비율은 그대로다. **묶는 일을 하는 것은 절대값이 아니라 비율이므로 아마 괜찮지만, 그 판정을 한 사람이 없다.** 최상위 그룹 사이의 실제 여백은 제목 **위** 4(항목 `margin-bottom`) + 8(리스트 패딩) + 16(헤딩 패딩) = 28px, 제목 **아래** 8(헤딩 패딩) + 8(리스트 패딩) = 16px 이다. 28 대 16 이라 제목이 아래로 묶인다. 하위 헤딩은 8/8 로 대칭이다.

- **볼 것:** 문서 셸의 좌측 네비게이션과 `ns-nav-group` 절의 첫 데모에서 ① 제목이 **자기 아래 목록**에 묶여 보인다 — 위 그룹의 마지막 항목에 붙어 그 그룹의 끝처럼 보이지 않는다 ② 하위 헤딩(대칭 8/8)도 자기 아래 항목에 묶여 보인다 ③ 최상위 그룹을 전부 접었을 때(A-16 ⑤ 의 상태) 남은 제목 다섯 줄의 간격이 고르다 ④ 라이트·다크 양쪽에서 같다
- **무엇이 잘못된 것인가:** 제목이 위 항목에 붙어 그 그룹의 마지막 줄처럼 보인다(묶임이 뒤집힌 것) · 제목 아래 여백이 위보다 넓어 보인다 · 전부 접은 목록에서 제목 줄 간격이 들쭉날쭉하다
- **A-23 과 같은 축이다.** 그룹 사이 24px 이 없어진 것과 이 값이 같은 세로 리듬을 나눠 지므로 **두 항목을 붙여서 본다.** 하나만 보면 원인을 잘못 짚는다
- **릴리스 때 할 일:** 묶임이 뒤집혔으면 이번 릴리스를 막는다. "좁다" 는 느낌만이면 막지 않고 A-23 과 함께 별도로 판단한다
