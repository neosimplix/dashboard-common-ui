# 다음 릴리스 전에 사람이 봐야 하는 것

`.claude/rules/verification.md` 가 이 저장소의 회귀 확인 수단을 둘로 못박는다 — `npm run check` 와 `index.html` 육안 확인. **두 번째 수단은 볼 것의 목록이 있어야 작동한다.** 이 파일이 그 목록이다.

지금 담긴 것은 2026-08-19 소비자 피드백 사이클(`docs/superpowers/specs/2026-08-19-consumer-feedback-0.2.5-design.md`)이 만든 것이고, 대상은 0.2.5 다음 릴리스다.

## 이 파일을 다루는 법

- **살아 있는 목록이다. 릴리스가 나가면 비운다.** 항목의 가치는 "바뀌었는데 아직 아무도 눈으로 안 봤다" 하나뿐이라, 확인이 끝난 항목은 소음이다. 낡은 항목이 쌓인 목록은 없는 것보다 나쁘다 — 훑고 넘기는 습관을 만들고, 그 습관은 다음 사이클의 진짜 새 항목까지 함께 넘긴다.
- **누적 로그로 만들지 않는다. 그 일은 git 이 이미 한다.** `git log -p docs/pending-human-checks.md` 가 사이클마다 무엇을 봐야 했는지를 그대로 준다. 파일 안에 이력을 또 쌓으면 중복이고, 둘이 어긋나면 낡는 쪽은 언제나 파일 안이다.
- 비울 때는 아래 두 절을 지우고 `## 대기 없음` 한 줄을 남긴다. 파일을 지우거나 비워 두지 않는다 — 그러면 "지금 정말 대기가 없다" 와 "아무도 안 채웠다" 가 구분되지 않는다.
- 항목을 더할 때는 **무엇을 보나** 와 **무엇이 잘못된 것인가** 를 함께 적는다. 하나만 있으면 보는 사람이 판정할 수 없고, 판정할 수 없으면 정상인 변화를 결함으로 신고하는 쪽으로 기운다. 아래 A 항목의 절반은 그 오인을 미리 막으려고 있다.
- **B 를 A 보다 먼저 둔다.** A 는 `index.html` 을 열면 어차피 눈에 걸리지만, B 는 여기 적혀 있지 않으면 존재조차 알 수 없다.

## B. 이 저장소에서는 재현할 수 없다 — 소비자 프로젝트가 필요하다

> **`npm run check` 가 초록인 것은 아래 넷에 대해 아무 증거도 아니다.**

`index.html` 에는 **React 가 없고, Tailwind 가 없고, 번들러가 없다.** 아래 넷은 그 셋 중 하나 이상을 필요로 한다. 소비자 프로젝트(`project01-test` — Next.js 16 · React 19 · Tailwind v4 대시보드)에서 본다.

**이 사이클이 고친 넷 각각에 소비자 환경에서만 드러나는 몫이 하나씩 있다** — 설계 §1 → B-1, §2 → B-2, §3 → B-3, §5 → B-4. 여기를 건너뛰면 "고쳤다" 의 증거가 하나도 없는 채로 태그가 나간다.

### B-1. React 제어 체크박스와의 조합 (설계 §1)

이번 사이클이 고친 진짜 버그이고, **이 저장소에는 확인할 방법이 아예 없다.** `index.html` 의 체크박스는 소비자가 상태를 되돌리지 않는 순수 DOM 체크박스라, `change` → `click` 이동으로 고친 그 경합이 애초에 일어나지 않는다. **A-1 이 초록인 것은 "회귀가 없다" 는 뜻이지 "버그가 고쳐졌다" 는 뜻이 아니다.**

- `checked={selected.includes(id)}` + no-op `onChange={() => {}}` 로 쓴 표에서 행 선택이 실제로 되는지
- 0.2.5 에서 쓰던 `defaultChecked` + `ref` 우회를 **지워도** 되는지
- 전체 선택 3-상태가 React 쪽 상태와 어긋나지 않는지

**잘못된 것:** 클릭한 체크가 즉시 되돌아간다. 그것이 0.2.5 의 증상 그대로다. 메커니즘은 `src/components/table/ns-table.ts` 의 `#onClick` 주석에 있다.

### B-2. 하이드레이션 경고 소멸 (설계 §2)

`hydrateRoot` 가 있어야 관찰되는 현상이다. 정렬 헤더가 있는 Next.js 페이지를 열어 **콘솔이 깨끗한지** 본다. `A tree hydrated but some attributes … aria-sort="none"` 이 더는 나오지 않아야 한다.

**`default-sort-key` 로 처음부터 정렬된 표는 여전히 경고가 난다.** 그것은 진짜 상태 변화라 지울 수 없고, 그 소비자는 서버 마크업에 같은 `aria-sort` 를 직접 렌더해야 한다(`index.html` 의 SSR 안내). **그 경우까지 조용해지길 기대하지 않는다** — 기대하면 정상을 결함으로 신고하게 된다.

### B-3. CSS 임포트 자리 (설계 §3) — 가장 위험한 항목

레이어 순서 사고는 Tailwind 와 번들러가 있어야 재현된다. `README.md` 의 새 예시(`@layer theme, base, ns-controls, components, utilities;` 가 맨 위, 두 CSS 임포트가 그 아래, `globals.css` 한 파일)를 **그대로** 따라 구성하고 확인한다.

```js
getComputedStyle(document.querySelector(".ns-button--outline")).borderTopWidth
// "1px" 이어야 한다. "0px" 이면 preflight 가 이긴 것이다.
```

**경고도 에러도 없다.** 눈으로 테두리를 찾는 것보다 위 한 줄이 확실하다.

### B-4. React `Card` 의 머리-본문 렌더 결과 (설계 §5)

`docs/consumer-example.tsx` 는 프롭 **타입만** 검사하고 아무것도 렌더하지 않는다. `index.html` 에는 React 가 없다. 따라서 **클래스 이름을 틀리게 적거나 중첩을 틀리게 짜도 `npm run check` 가 통과하고 `index.html` 에서도 영영 안 드러난다.**

개발자 도구로 클래스 이름을 직접 대조한다. `src/react/controls/Card.tsx` 가 `heading` 을 받았을 때 내야 하는 것은 이것이다.

```
.ns-card
├─ .ns-card__header
│  ├─ div                        (이름 없는 감싸개)
│  │  ├─ h2|h3.ns-card__title
│  │  └─ p.ns-card__description  (description 을 줬을 때만)
│  └─ .ns-card__actions          (actions 를 줬을 때만)
└─ .ns-card__body
```

- 이름 없는 감싸개 `<div>` 가 실제로 그려지는지 — 빠지면 `.ns-card__header` 의 `justify-content: space-between` 이 설명을 오른쪽 끝으로 민다
- `headingLevel` 이 `2`(기본)와 `3` 에서 각각 `<h2>`/`<h3>` 를 내는지
- **`heading` 없이 쓴 기존 호출부의 출력이 예전과 완전히 같은지** — `.ns-card` 하나에 자식이 그대로 들어간 모양이어야 한다. 이것이 "기존 소비자가 안 바뀐다" 는 약속의 본체다

## A. 이 저장소의 `index.html` 에서 확인한다

`npm run demo` 로 빌드하고 연다. 릴리스 직후에는 `dist/` 가 사라지므로 다시 빌드해야 한다.

### A-1. 표 선택 (설계 §1)

`#table-select-demo` · `#table-both-demo` 에서 본다.

- 행 체크박스를 눌러 선택·해제가 되는지, 체크박스에 포커스를 두고 **Space** 로도 같은지
- 전체 선택 체크박스가 3-상태를 보이는지 — 행이 일부만 선택되면 indeterminate(가로줄), 전부면 체크, 하나도 없으면 빈 칸
- 전체 선택을 누르면 행 전부가 그 값을 따라가는지
- **체크박스 네모 바깥의 라벨 영역**을 눌러도 토글이 **한 번만** 일어나는지

마지막 항목은 누를 자리를 찾기가 어렵다. 표 데모의 `.ns-checkbox` 에는 글자(`<span>`)가 없지만, 그 라벨은 `display: flex` 라 셀 폭을 채우고 `padding: var(--ns-space-1-5) 0` 을 갖는다 — **체크박스 오른쪽의 빈 자리와 위아래 여백**이 라벨만 있는 클릭 영역이다.

**잘못된 것:** 그 자리를 한 번 눌렀는데 체크가 켜졌다 꺼진다(같은 클릭이 두 번 처리됐다는 뜻). 정상이면 한 번만 토글된다.

### A-2. `aria-sort` (설계 §2)

**`#sort-demo` 에서 본다** — `ns-table` 이 `aria-sort` 의 유일한 작성자인 데모이고, 처음에는 어느 칼럼도 정렬돼 있지 않다.

**`#table-sort-states-demo` 로는 이 항목을 확인할 수 없다.** 그 표는 `ns-table` 로 감싸지 않고 `aria-sort` 를 마크업에 손으로 써 둔 정적 예시다(감싸면 컴포넌트가 손으로 쓴 값을 덮어쓰므로 일부러 그렇게 돼 있다).

- 개발자 도구로 정렬되지 않은 `th` 를 보면 `aria-sort` 속성이 **아예 없는지** (`"none"` 이 아니라 부재)
- 정렬하면 `ascending`/`descending` 이 붙고, 같은 칼럼을 3-상태 한 바퀴 돌려 해제하면 **다시 사라지는지**
- 정렬되지 않은 칼럼에서도 삼각형이 `opacity: 0` 으로 **자리를 지켜 헤더 폭이 흔들리지 않는지** (`#table-sort-states-demo` 가 이 항목의 정적 대조본이다 — 세 상태가 한 줄에 나란히 있다)

> **먼저 읽을 것 — 헤더 행이 이 사이클에서 약 4px 낮아진다. 회귀가 아니다.**
>
> 원인은 A-3 의 `th` 줄높이 변화(`1.25rem` → `1rem`)이고 **`aria-sort` 작업과 무관한 부수효과**다. `.ns-table__sort` 는 `font: inherit` 라 그 줄높이를 그대로 물려받으므로, **정렬 버튼이 라벨과 삼각형을 통째로 데리고 4px 만큼 짧아지고 그만큼 위치가 옮겨간다.**
>
> **삼각형이 자기 라벨을 기준으로 움직이지는 않는다.** `.ns-table__sort` 는 `inline-flex` 이고 아이템이 둘이다 — 라벨 글자를 감싸는 익명 플렉스 아이템(높이 = 줄높이)과 `::after`(테두리로 그린 `.5rem × .3rem` 상자). 교차축 크기는 둘 중 큰 쪽이라 곧 줄높이이고, `align-items: center` 가 라벨과 삼각형을 **같은 중심선**에 맞춘다. 둘의 상대 위치는 불변이다.
>
> 그러니 **삼각형만 따로 보지 말고 헤더 행 전체의 높이를 본다.** 삼각형을 자기 라벨과 대조하면 아무 차이도 안 보이고, 그러면 이 경고가 틀렸다고 결론 내리게 된다 — 이 경고가 막으려는 것과 정확히 반대다.

### A-3. 문서 페이지 표 규칙에 가드가 붙었다 — 표 데모 일곱 개 전부

`index.html` 의 `<style>` 은 레이어에 들지 않고 `dist/controls.css` 는 `@layer ns-controls` 라, 이 페이지의 `table`/`th`/`td` 규칙이 특정도와 무관하게 `.ns-table` 을 이기고 있었다. `:not(:where(.demo *, ns-dialog *))` 를 붙이면서 아래 **일곱 가지**가 동시에 바뀐다. 전부 "라이브러리가 원래 그리려던 모양" 으로 돌아가는 것이라, **다르게 보이는 것 자체는 정상이다.**

| 무엇 | 전 (페이지 규칙이 이김) | 후 (`.ns-table` 이 그림) |
|---|---|---|
| **마지막 행 구분선** | **그어져 있었다** | 없다 (`tbody tr:last-child td { border-bottom: 0 }`) |
| `td` 세로 정렬 | `top` | `middle` |
| `th` 세로 정렬 | `top` | `middle` (UA 기본값으로 복귀) |
| `td` 글자 크기 | `xs` (.75rem) | `sm` (.875rem, `.ns-table` 에서 상속) |
| `th` 줄높이 | `sm` (1.25rem) | `xs` (1rem) — **헤더 행이 약 4px 낮아진다** |
| `td` 패딩 | `space-2 space-3` | `space-3` (사방) — **세로만 늘어난다.** 가로는 양쪽 다 `space-3` 이라 폭에 기여하지 않는다 |
| `<table>` 바깥 여백 | `space-4 0` | 없음 — 데모 패널 안에서 위아래로 붙는다 |

`th` 의 글자 크기·패딩·색·굵기·아래 테두리·좌측 정렬은 양쪽이 같은 값이라 **바뀌지 않는다.** `td` 줄높이도 양쪽 다 `1.25rem` 이라 그대로다.

대상 데모는 `.demo` 안에 `.ns-table` 이 있는 **일곱** 개이고 그것이 전부다: `#table-demo` · `#table-narrow-demo` · `#table-sort-states-demo` · `#table-row-click-demo` · `#sort-demo` · `#table-select-demo` · `#table-both-demo`.

**특히 볼 곳은 셋이다.**

- **`#table-select-demo` · `#table-both-demo`** — `th` 세로 정렬 변화가 눈에 보이는 유일한 두 곳이다. 이 두 데모의 헤더 행만 `<th>` 안에 `.ns-checkbox` 라벨(약 `1.75rem`)과 평범한 글자 `th` 를 섞어 놓아서, 글자 헤더들이 **위 정렬에서 세로 가운데 정렬로** 몇 px 옮겨간다. **A-1 의 선택 동작 확인도 같은 데모에서 하므로 한 번에 본다.**
- **`#table-sort-states-demo`** — 헤더 행이 4px 낮아지면서 정렬 버튼이 라벨·삼각형을 통째로 데리고 움직인다. 오독을 막는 설명은 **A-2 의 인용 블록**에 있다.

**`#table-narrow-demo` 는 위험 지점이 아니다.** 7 칼럼에 전체 URL 한 칸과 버튼 세 개짜리 액션 칸이 들어 있고 컨테이너는 `max-width: 26rem` 이라, `min-width: max-content` 가 이미 컨테이너를 한참 넘는다. 여기서 폭을 바꾸는 것은 `td` 글자 크기(`xs`→`sm`) **하나뿐이고**(패딩 변화는 세로 전용이다) 그것도 넓히는 방향이라, **가로 스크롤은 사라질 수 없다.** 더 세게 넘칠 뿐이다.

`code` 규칙에는 가드를 붙이지 않았으므로 **`code` 로 바뀌는 화면은 없다.** `#tokens` 절의 스와치 라벨 19 개는 그대로다 — 붙이지 않기로 한 기준과 그 19 개의 출처(마크업이 아니라 배선 스크립트)는 `index.html` 의 `<style>` 주석에 적혀 있다.

### A-4. `.ns-card` 머리-본문 (설계 §5)

- `#card-demo`(머리 없음)와 `#card-header-demo`(머리 있음)를 나란히 놓고 **머리 없는 쪽의 패딩이 예전 그대로인지**
- 구분선이 카드 폭 전체가 아니라 **내용 폭까지만** 그어지는지. 전체 폭으로 긋지 않는 것은 의도다 — `--ns-card-padding` 이 `.ns-card` 자신에게 있어서, 전체 폭으로 그으려면 그 패딩을 `__header`·`__body` 로 내려야 하고 그러면 머리 없이 쓰던 기존 호출부의 패딩이 경고 없이 사라진다
- 제목이 길 때 액션이 찌그러지거나 줄바꿈되지 않는지 (`.ns-card__actions` 가 `flex-shrink: 0`). **데모의 제목은 짧아서 그대로는 안 보인다** — 개발자 도구에서 `.ns-card__title` 의 글자를 길게 바꿔 놓고 본다
- 다크모드에서 같은지

### A-5. 명령형 대화상자의 본문 크기

`#confirm-demo` 의 세 버튼(`nsAlert` · `nsConfirm` · `nsConfirm (danger)`)이 띄우는 대화상자의 **본문 글자가 커진다** — 이 페이지의 `p` 규칙(`sm` · 1.7)을 받던 것이 가드 목록의 `ns-dialog *` 때문에 이제 대화상자에서 상속받는다(브라우저 기본 16px · `normal`). 확인할 것은 하나다.

> `#dialog-demo` 의 대화상자를 열어 본문을 보고, 이어서 `#confirm-demo` 의 대화상자를 열어 본문을 본다. **두 본문의 크기가 같아야 한다.** 지금까지 달랐다.

색은 안 바뀐다 — `ns-dialog` 의 shadow 가 `<dialog>` 에 `--ns-color-fg-body` 를 이미 세운다.

줄높이는 1.7 → `normal` 이라 **여러 줄 메시지에서 줄 간격이 좁아 보일 수 있다.** 좁아서 읽기 나쁘면 고칠 자리는 이 페이지가 아니라 `ns-dialog` 의 `.body` 다(지금 `.body` 는 글자 크기도 줄높이도 정하지 않는다). 라이브러리 변경이므로 이번 사이클에서 하지 않았다.

### A-6. 아코디언 데모의 "커 보이는 본문" — 결함이 아니다

`p` 가드가 붙은 뒤로, `#accordion-demo` 의 본문 채움 글(`<p style="margin:0">닫힌 채로 시작한다.</p>` 등 셋)이 **아코디언 자신의 제목보다 크게** 렌더된다. `.ns-accordion__title` 은 `--ns-font-size-sm`(0.875rem)인데 본문 `<p>` 는 이제 아무 규칙도 안 받아 `body` 에서 상속받은 16px 이기 때문이다.

**버그가 아니다.** 스타일 없는 `<p>` 가 소비자 페이지에서 갖는 값이 정확히 그것이고, 아코디언 본문 타이포그래피는 라이브러리가 정하지 않는다(`.ns-accordion__body` 는 레이아웃만 준다). 하지만 **읽는 사람이 결함으로 오인할 가장 유력한 한 곳**이라 미리 적어 둔다.

데모로서 어색하다고 판단되면 고칠 자리는 **데모 마크업**(그 `<p>` 에 실제 소비자가 쓸 법한 클래스를 주는 것)이지 페이지 `<style>` 이 아니다. 가드를 되돌리면 A-3 이 고친 것이 함께 되돌아간다.

**같은 가드가 모든 데모의 꾸미지 않은 `<p>` 에 걸린다** — `#card-demo`·`#card-header-demo` 의 채움 글도 커진다. 반대로 라이브러리 클래스를 가진 산문(`.ns-card__description` · `.ns-message p` · `.ns-multi-select__empty`)은 페이지 규칙 대신 자기 클래스의 크기·색을 보이게 된다. 아코디언은 그중 **차이가 가장 눈에 띄는 곳**일 뿐이고, 나머지도 판정 기준은 같다: 데모가 라이브러리가 그리는 모양을 보여주게 된 것이 이 변화의 목적이다.
