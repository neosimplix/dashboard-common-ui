# `ns-dialog` 초기 포커스 설계

**날짜:** 2026-09-01
**대상:** v0.5.3 (헤더 밑줄 수정과 같은 태그)

## 문제

대화상자를 열면 닫기 버튼(`×`)에 검정 테두리가 생긴다. 대화상자 안의 다른 곳을
클릭하면 사라진다.

그 테두리는 브라우저 기본 링이 아니라 **우리 것**이다.

```css
/* ns-dialog.styles.ts */
.close:focus-visible { outline: 2px solid var(--ns-color-accent); outline-offset: 2px; }
```

밝은 모드의 `--ns-color-accent` 는 `oklch(21% 0.006 285.885)` 로 거의 검정이다
(`--ns-color-accent-fill` 과 같은 값이라 `승인` 버튼의 채움색과 구분되지 않는다).
실측한 계산값도 `2px solid oklch(0.21 0.006 285.885)` 였다.

포커스가 그 버튼에 가는 이유는 `showModal()` 의 초기 포커스 규칙이다. 대화상자의
focus delegate 는 **자손 중 첫 포커스 가능 요소**를 고르고, DOM 순서상 그것이
헤더 안의 `.close` 다. 그다음 링이 보이는지는 엔진이 갈린다.

## 측정

두 엔진에서 직접 쟀다(Blink: 헤드리스 Chrome, WebKit: `WKWebView` 하네스).

| 경우 | Blink 초점 | Blink 링 | WebKit 초점 | WebKit 링 |
|---|---|---|---|---|
| 현재 | `.close` | **뜬다** | `.close` | 안 뜬다 |
| 섀도 `<dialog tabindex="-1">` | `.close` | 뜬다 | `.close` | 안 뜬다 |
| 섀도 `<dialog tabindex="-1" autofocus>` | `.close` | 뜬다 | `dialog` | 안 뜬다 |
| 소비자가 슬롯 버튼에 `autofocus` | 승인 버튼 | 안 뜬다 | `.close` | 안 뜬다 |
| **`h2[tabindex="-1"]`** | **`h2`** | UA 링 | **`h2`** | 안 뜬다 |
| `h2[tabindex="-1"]` + 소비자 `autofocus` | 승인 버튼 | 안 뜬다 | `h2` | 안 뜬다 |

여기서 나오는 사실 넷:

1. **Chrome 은 모달의 초기 포커스를 의도적으로 `:focus-visible` 로 친다.** WebKit 은
   그렇게 하지 않는다. 그래서 같은 코드가 Safari 에서는 멀쩡해 보인다.
2. **`<dialog>` 자신의 `autofocus` 를 Chrome 은 무시한다.** focus delegate 탐색이
   자손만 보기 때문이다. WebKit 은 따른다.
3. **`<dialog tabindex="-1">` 만으로는 아무 효과가 없다.** 포커스 가능한 자손이
   있으면 그쪽이 먼저 선택되므로 조상의 `tabindex` 는 후보가 되지 못한다.
4. **소비자의 슬롯 `autofocus` 는 Chrome 에서만 통한다.** WebKit 은 슬롯 배정된
   light DOM 을 후보 탐색에서 보지 않는다. `confirm.ts:123` 의 주석이 *"autofocus
   후보 탐색이 닿는지가 구현에 달렸다"* 고 적어 둔 것이 이번에 확정됐다.

## 결정

**초기 포커스를 제목(`h2`)이 받게 하고, 그 요소의 포커스 링만 끈다.**

포커스를 아예 주지 않는 선택지는 없다 — `showModal()` 은 반드시 포커스를 대화상자
안으로 옮기고, 그래야 포커스 트랩·`Esc`·`::backdrop` 과 스크린리더 맥락이 성립한다.
바꿀 수 있는 것은 **어디에 주느냐** 뿐이다.

### 변경 둘

`src/components/dialog/ns-dialog.ts` 의 `render()`:

```ts
<h2 id="dialog-heading" tabindex="-1">${this.heading}</h2>
```

`src/components/dialog/ns-dialog.styles.ts`:

```css
#dialog-heading:focus { outline: none; }
```

`:focus-visible` 이 아니라 `:focus` 를 쓴다 — 상위집합이라 엔진이 어느 쪽으로 링을
거는지에 의존하지 않는다. **JS 는 바뀌지 않는다.** `updated()` 의 `showModal()`
호출도, `confirm.ts` 의 `focusInitial` 도 그대로다(`nsConfirm` 은 자기 푸터 버튼에
명시 포커스를 주므로 이 경로를 타지 않는다).

### 이 변경이 지키는 것

- **탭 순서가 바뀌지 않는다.** `tabindex="-1"` 은 탭 순서에 들어가지 않고 프로그램
  포커스만 받는다. 열린 뒤 `Tab` 을 누르면 지금처럼 `×` 로 간다.
- **소비자 `autofocus` 가 여전히 이긴다**(Chrome). 측정으로 확인했다. 기존에 있던
  탈출구를 깨지 않는다.
- **스크린리더가 열릴 때 제목을 읽는다.** 컨테이너/제목에 초기 포커스를 주는 것은
  WAI-ARIA APG 가 권하는 형태다.

### 버린 접근 둘

- **`×` 를 그대로 두고 첫 포커스일 때만 링을 숨긴다.** "열려서 받은 포커스" 와
  "`Tab` 으로 돌아온 포커스" 를 구별하는 JS 상태가 필요하고, 잘못 만들면 키보드
  사용자가 `×` 로 이동했을 때도 링이 사라진다. **접근성을 실제로 깎는 유일한 안**이라
  버렸다.
- **푸터의 주 버튼에 자동 포커스.** 선언형 `ns-dialog` 는 푸터가 소비자 슬롯이라
  무엇이 주 버튼인지 알 수 없다. `승인` 같은 것에 기본 포커스가 가면 `Enter` 한
  번에 실행된다. `nsConfirm` 이 이것을 하는 이유는 자기가 버튼을 직접 만들어 어느
  쪽이 주인지 알기 때문이고, 선언형에는 그 정보가 없다.

## 규칙과의 충돌 — `outline: none` 에 되돌릴 규칙을 두지 않는 근거

`library-invariants.md` 에 **"shadow 스타일이 UA 기본값을 덮으면 되돌릴 규칙을 함께
둔다"** 가 있고 `outline: none` 이 정확히 그 행위다. 여기서는 되돌릴 규칙을 두지
않는데, 근거는 "안 두어도 된다" 가 아니라 **되돌릴 대상이 없다** 다.

`tabindex="-1"` 인 요소는 탭 순서에 들어가지 않으므로 **키보드로 이 `h2` 에 도달하는
경로가 존재하지 않는다.** 링이 필요해지는 상황(사용자가 키보드로 그 요소에 이동해
자기 위치를 확인해야 하는 상황)이 발생하지 않는다. 규칙이 막으려는 성질 — 키보드
사용자가 포커스 위치를 잃는 것 — 은 그대로 지켜진다.

이 근거를 **스타일 주석과 `docs/gotchas.md` 양쪽에 적는다.** 적지 않으면 다음
사람이 규칙 위반으로 읽고 되돌린다.

**불변 규칙은 추가하지 않는다.** 대화상자가 하나뿐이라 사용처가 하나인 규칙이 되고,
저장소가 토큰에 대해 이미 갖고 있는 기준("사용처가 하나인 토큰을 만드는 것은
추측이다")을 같은 모양으로 적용한다. 근거는 `gotchas.md` 에 남기고, 모달이 둘째로
생기는 날 규칙으로 올린다.

## 문서

- **`docs/gotchas.md`** — 새 절. 위 "측정" 의 사실 넷을 담는다. 특히 2·3 은 **다음
  사람이 똑같이 시도할 처방**이라 "해봤고 안 된다" 를 남기는 값이 있다.
- **`guide.html`** 대화상자 절 — 열리면 초기 포커스가 제목에 가고 그래서 어떤 버튼도
  눌린 것처럼 보이지 않는다는 한 문단. **소비자 `autofocus` 는 적지 않는다** —
  Chrome 에서만 통하고 WebKit 은 무시하므로(측정됨) 지원 기능으로 광고하면 거짓이
  된다. 그 사실은 `gotchas.md` 에만 남긴다.
- **`changelog.html` 의 v0.5.3 절과 `README.md` 릴리스 표 행** — 이미 헤더 밑줄로
  만들어 둔 절에 항목을 더한다. 표의 한 줄 요약도 둘을 담게 고친다.

## 검증

테스트 러너는 없다(설계 결정). 수단은 둘이다.

**정적** — `npm run check` 5개, 그리고 `guide.html` 을 고치므로
`.claude/rules/verification.md` 의 문서 페이지 구조 검사 넷(기대값은 파일마다 다르다:
`index` 0, `guide`·`changelog` 1).

**실측** — 헤드리스 프로브로 두 엔진에서 넷을 잰다.

1. 초기 포커스가 `h2#dialog-heading` 인가
2. `.close` 와 `h2` 어느 쪽에도 링이 없는가 (`matches(":focus-visible")` 와 계산된
   `outline-style` 둘 다)
3. `Tab` 한 번에 `×` 로 가는가 (탭 순서 보존)
4. 소비자가 슬롯 버튼에 `autofocus` 를 주면 그쪽이 이기는가 (Chrome)

**검사는 실패시켜 본다.** `tabindex` 를 떼고 같은 프로브를 돌려 `.close` + 링이
실제로 재현되는지 확인한 뒤에 고친 상태를 잰다. 한 번도 실패해본 적 없는 프로브가
통과하는 것은 증거가 아니다.

**사람 눈이 필요한 것** — 실제 Chrome·Safari 에서 마우스로 열어 링이 없는지, `Tab`
을 눌렀을 때 `×` 에 링이 정상적으로 뜨는지, 스크린리더가 제목을 읽는지.
